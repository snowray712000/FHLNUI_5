
## 規畫

看完這些 Case，我的想法是：**中繼資料要先分「段落類型」再分「行內元素」**，這樣後續 DText[] 才穩定。

**建議的中繼資料分層**
- **Block 層級（段落型）**
  - `summary`（章節摘要）
  - `keyword`（* 開頭的關鍵字/片語）
  - `refOnly`（只有 #...| 的段落）
  - `note`（無 # 的註腳/說明文字）
  - `empty`（只剩 `# 13|` 這種「原書無此節」）
- **Inline 層級（行內元素）**
  - `text`（一般文字）
  - `ref`（#...| 交互參照）
  - `orig`（[vav,] 這類原文片段）
  - `fb`（\<FB>...\<Fb>）

**規則觀察重點**
- `*` 開頭表示「keyword block」，後面可能有 **註腳**、也可能有 **ref 群組**。
- `# ... |` 可能多段、**應合併為同一個 ref 群**（不要視為原書分段）。
- 只有 `# ... |` 且前面無 `*` ⇒ 視為 **refOnly block**。
- 章節摘要只出現在 **第 1 節**且在第一個 `\n\n` 之前。
- `# 13|` 這種 ⇒ **empty block**（可渲染為「本節無串珠」或保持空）
- `*marg:` 是 **ref 的註腳**，建議作為 `note` inline 並與 ref 關聯。

**關於 DText**
- 若你只想用 `{w, isRef}`，可先行，但可能會失去 **註腳/原文/FB** 的結構資訊。
- 建議最少加一個 `tp`（或 `kind`）欄位，以免日後又要重構。

## 1) 中繼資料 Schema（草案）

```json
{
  "blocks": [
    {
      "type": "summary | keyword | refOnly | note | empty",
      "keyword": "string|null",
      "items": [
        { "type": "text", "w": "string" },
        { "type": "ref", "w": "string" },
        { "type": "orig", "w": "string" },
        { "type": "fb", "w": "string" }
      ],
      "raw": "string"
    }
  ]
}
```

**說明**
- `blocks[]`：段落層級
- `type`：段落類型  
- `keyword`：僅 `keyword` block 有值（`* xxx.`）  
- `items[]`：行內元素，**未來可映射成 DText[]**  
- `raw`：保留原始字串，方便除錯與回溯

## 2) 解析規則草案

### A. Block 分段規則
1. 先以 **雙換行 `\n\n`** 分段為 block  
2. 去頭尾空白  
3. 空字串跳過  

### B. Block 類型判斷
按順序套用：

1. **summary**  
   - 僅第 1 節，且在第一個 `\n\n` 前  
   - 含多行 `n; ...;` 章節摘要  
2. **keyword**  
   - 以 `* ` 開頭  
   - 直到第一個 `.` 結束為 keyword  
3. **refOnly**  
   - **不含 `* `**  
   - 但含 `# ... |`  
4. **empty**  
   - 只有 `# 13|` 這種單一節標記  
5. **note**  
   - 以上都不是，屬一般註腳/說明文字  

### C. Inline item 解析規則
1. **ref**  
   - 以 `#` 起始，直到 `|` 結束  
   - 同一 block 內的多段 `#...|` **合併為一個 ref item**  
2. **orig**  
   - `[...]` 形式（例：`[vav,]`）  
3. **fb**  
   - `\<FB> ... \<Fb>` 片段  
4. **text**  
   - 其餘文字  

### D. 特殊規則
- `*marg:` 視為 **text** 或 **note**（建議保留在 ref block 的 items 中）  
- `Heb.` 這類註腳，歸入 **text**  
- keyword block 內可同時包含：`text + ref` 或僅 `text`
