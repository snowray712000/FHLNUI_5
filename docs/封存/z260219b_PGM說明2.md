# PGM：註釋解析與 Inline 解析設計

## 摘要
本設計以「解析結果可重用、輸出穩定、向下相容」為原則，將註釋文字處理分成**結構化解析**與**行內語彙解析（Inline）**兩層。主輸出維持中立的 DocNode（含原文 `w`），同時提供可選的 `inline`（DText[]）以支援交互參照（如 `#創1:2|`）與原文編號（如 `SNH/SNG`）的互動渲染。流程既保持下游自由度，又能共享一致的偵測結果。

## 前言（情境）
註釋資料來源為長期累積的純文字，含縮排、清單、表格、註解與跨行內容。現有解析流程已建立自 `parseComment` 的多階段管線（如 `preprocessCaseToLines`、`detectTableBlocks`、`tokenizeLine`、`buildTree`、`normalizeTree`），並能產生 DocNode 供渲染使用。現在需求是加入交互參照與原文 SN 的偵測與呈現，且此偵測需可套用於一般文字、JSON table、table cell 等多種來源。

## 動機（Problems）
1. **行內語彙偵測散落**  
   若在渲染階段才做 `#...|` 與 `SNH/SNG` 偵測，將導致規則分散、結果不一致，且難以測試。

2. **資料來源多樣**  
   交互參照與 SN 可能出現在一般段落、table cell、JSON table 的 `text` 等處，若各處都各自解析，成本與錯誤風險提升。

3. **相依耦合風險**  
   若主輸出直接改為 DText[]，將迫使所有下游依賴 DText 結構，降低可用性與擴展性。

## 目的（Goals）
1. **保持主輸出中立**  
   `parseComment` 的主輸出仍為 DocNode（含 `w`），不強迫下游依賴 DText。

2. **提供可選 Inline 解析成果**  
   透過新增可選 `inline` 欄位（DText[]），讓需要互動的場景可直接使用，不需重做偵測。

3. **建立一致且可測的偵測流程**  
   將 `#...|` 與 `SNH/SNG` 的偵測規則集中於單一模組，便於測試與維護。

## 方法（Methods）
1. **既有結構化管線維持不變**  
   仍以 `parseComment` 為入口，依序執行：
   - `preprocessCaseToLines`：行切分與前處理  
   - `detectTableBlocks`：表格區塊偵測  
   - `tokenizeLine`：行級 token  
   - `buildTree`：語意樹  
   - `normalizeTree`：DocNode 標準化

2. **新增 Inline 解析階段（建議插入點）**  
   - 建議位置：`normalizeTree` 之後（或內部）  
   - 對每個 DocNode 的 `w` 進行行內解析，產生 `inline: DText[]`  
   - 對 `joTable` 的 cell `text` 亦套用同一解析（可在 `normalizeTree` 或後處理中完成）

3. **輸出策略**  
   - DocNode 保留 `w` 供一般使用  
   - `inline` 為可選欄位，僅需互動渲染者使用  
   - 渲染層可優先使用 `inline`，若無則 fallback `w`

4. **偵測規則集中**  
   交互參照（`#...|`）與 SN（`SNH/SNG`）偵測集中在一個 inline parser，以利一致性與單元測試。
