以下是四個 bug 各自的重現方式（在舊版網站 https://bible.fhl.net 上操作），修好之後可以拿同一組步驟回去確認：

Bug 1：章節範圍文字組字錯誤（節號消失）

現象：閱讀畫面顯示的「N章M節至N章M節」範圍文字，節號那段完全不見，只剩「N章至N章」。

重現條件：需要一筆 bsec 或 esec 不是 0 的典藏資料。逆向報告裡沒有現成的真實樣本（樣本剛好都是 bsec=esec=0），所以要重現得自己先找：

抱歉，上面那次工具呼叫是我操作失誤（重新讀了規劃文件開頭一行，沒有實際內容）。以下直接回答，不需要再讀檔案：

Bug 1：章節範圍文字組字錯誤（節號消失）

成因：res += re_record.bsec.toString() + this.props.isgb? "节": "節" 少了括號，?: 優先權比 + 低，實際被丟進 res 的是 bsec.toString() + isgb（字串接布林值的怪東西），後面的 "节"/"節" 判斷結果被丟棄。

現象：閱讀畫面本該顯示「1章2節至1章5節」，結果變成「1章至1章」——節號整段消失。

重現方式：這個 bug 觸發條件很單純：只要那筆典藏資料的 bsec 或 esec 不是 0（有記錄具體到「第幾節」而不只是「整章」）。逆向報告裡我實測的樣本（book=27 創1:1、創1:2）剛好 bsec=esec=0，不會觸發，所以我沒有一個「已驗證會出錯」的真實經節可以直接給你。

建議兩種找法：

直接打 API 找一筆非零樣本：對多本典藏書、多個章節跑 https://bible.fhl.net/json/sob.php?gb=0&book={id}&engs={書卷}&chap={章} 掃過去，找 bsec 或 esec 不為 0 的回應（id 可以先從 ob.php?gb=0 的清單裡挑幾本內容較細的著作試）。
不用真的找到會觸發的經文，直接針對函式單元測試：這個 bug 完全不依賴瀏覽器操作、可以脫離網路重現——把 re_record = {bchap:1, bsec:2, echap:1, esec:5, vid:1} 這種假資料直接丟進 content.render 對應的那段組字邏輯（或修好後對應的 format_ob_page_range()），比對輸出字串是不是「1章2節至1章5節」。這是我在規格文件裡建議的驗證方式，也是最省事、不需要找真實經文的做法。
Bug 2：sob.php 回應非法 JSON 時整個炸掉

現象：確定可重現，這個有現成的真實案例。

重現方式：直接開這個網址（book=27《勸世良言》，往下翻到超過總頁數）：

https://bible.fhl.net/json/sob.php?gb=0&book=27&page=15

或

https://bible.fhl.net/json/sob.php?gb=0&book=27&page=16

HTTP 狀態碼是 200，但 body 在 record 陣列開頭被塞進一段非 JSON 文字（Page number too large 15），不是合法 JSON。

在網站上實際操作重現：進典藏 → 選 id=27《勸世良言》→ 閱讀 → 一路按「下一頁」翻到 page=14（此時 next=14，代表卡在最後一頁附近）→ 再按一次下一頁，理論上會送出 page=15 這個請求，讓 JSON.parse 炸掉。修好前可以打開瀏覽器 devtools console，應該會看到 Uncaught SyntaxError；修好後應該改成畫面顯示 err_msg（錯誤訊息），console 不再報未捕捉例外。

Bug 3：多次請求競速，晚到的舊回應覆蓋新選擇

現象：連續快速點兩個不同的典藏書「閱讀」，畫面最後可能停在先點的那本而不是後點的那本（因為先送出的請求比較晚回應）。

重現方式：這個是網路時序問題，沒有固定會觸發的經文，正常網路環境下不一定每次都重現（要剛好發生回應倒序）。比較可靠的重現方法：

開瀏覽器 devtools → Network 面板，把節流（throttling）設成 Slow 3G 之類的慢速。
進典藏清單，連續快速點兩本不同書的「閱讀」按鈕（例如先點 id=27 再點 id=257）。
因為網路變慢，兩個請求的完成順序可能被打亂，觀察最後畫面停在哪一本——如果停在 id=27（先點的）而不是 id=257（後點的），就是重現了這個 bug。

或者更可控的方式（不依賴真實網路時序）：修改前先在其中一個 _query_sob_from_ajax_idxbook 的 callback 前手動加一行 setTimeout 延遲，模擬「先點的請求刻意晚回應」，這樣可以 100% 重現、也能 100% 驗證修好後的行為（畫面應該永遠停在最後一次點擊的那本）。

Bug 4：初始化多查一次頁

現象：頁面重新整理、資訊面板剛好停在「典藏」分頁時，會多發一次不必要的 sob.php 單書查詢請求。

重現方式：

在網站上切到資訊面板的「典藏」分頁，選一本書進入閱讀畫面。
重新整理整個網頁（讓 localStorage 的面板狀態記住「上次在典藏分頁」，網頁初始化時會自動恢復進典藏）。
開 devtools Network 面板，篩選 sob.php，觀察頁面剛載入時單書查詢請求發送了幾次。

預期（有 bug）：發送 2 次幾乎一樣的 sob.php?book={idxbook}&... 請求。
修好後：應該只發送 1 次。

小結：Bug 2（非法 JSON）是最容易重現的，我給的網址可以直接打開驗證；Bug 4（多查一次頁）也是穩定可重現的操作流程；Bug 1（組字錯誤）建議直接用單元測試驗證，不用花時間找真實經文；Bug 3（競速）建議用 devtools 節流或手動加延遲來穩定重現，靠自然網路時序不保證每次都能觸發
