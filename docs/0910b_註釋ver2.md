# 1. 功能名稱

- 名稱：**註釋**。
- 別稱／搜尋用字：注釋。
- 程式關鍵字：`Comment`、`comment`。
- 本次對象是經文的註釋輔助資料，不是程式碼註解。

# 2. 功能目的與資料背景

本節為使用者提供的領域背景與資料線索，尚待程式碼或 API 查證。

## 2.1 目的與資料來源

閱讀經文時，顯示目前經節對應的查經註釋，並允許使用者閱讀相鄰註釋段落、書卷背景，以及開啟內容中的原文詞典或經文參照。

註釋資料由信望愛核心成員逐步整理查經內容而形成。早期以整卷內容呈現，後來提供 API，供 app 整合。

- 整卷範例：[猶大書註釋](https://a2z.fhl.net/php/pcom.php?book=3&engs=Jude)。
- API 說明入口：[信望愛 JSON API](https://bible.fhl.net/json/)。
- 本功能使用的 API：`sc.php`。
- 本次註釋來源固定使用 API 參數 **`book=3`**。原稿猶大書範例中的 `book=4` 已由使用者確認為筆誤。
- **語意警告**：此 API 的 `book` 是「註釋書代號」，不是「聖經書卷代號」。專案中其他地方的 `book` 多半是聖經書卷編號，例如創世記為 1。分析時必須逐處辨識，不可混用。
- 猶大書範例：[Jude 1:1](https://bible.fhl.net/json/sc.php?book=3&engs=Jude&chap=1&sec=1&gb=0)。
- 馬太福音範例：[Matt 1:1](https://bible.fhl.net/json/sc.php?book=3&engs=Matt&chap=1&sec=1&gb=0)。

## 2.2 以範圍為單位的資料

- 註釋是範圍型資料，不一定一節對應一筆。
- 例如查詢猶大書 1:1，取得的註釋範圍可能是 1:1–1:2；查詢 1:2 會取得同一筆資料。
- 各段涵蓋的經節數不固定。
- 書卷背景通常以 `chap=0`、`sec=0` 查詢，屬於特殊參數。
- 不可由「同一範圍回傳相同內容」推斷前端一定有快取或請求去重；這些須另外查證。

## 2.3 純文字、空白與清單

資料源於 BBS 時代的純文字排版，不是 Word 或 Markdown。原文含有大量用於縮排、凸排與固定行寬折行的空白及換行。

原稿提供的片段如下；程式碼區塊中的 `\r\n` 表示換行序列：

```text
●家「譜」：SNG00976，「書卷」、「紀錄」。\r\n      ●「家譜」：SNG00976+SNG01078，「世系紀錄」、「家譜的記錄」或「歷史的記\r\n                  錄」、「起源」，此字就是七十士譯本「創世記」的標題。七十士\r\n                  譯本的#創 2:4;5:1|也出現這個字。\r\n
```

使用者以此說明：視覺上同一項目的文字可能跨多行，需理解哪些換行或空白是排版造成的，哪些代表內容結構。這不是要求本次修改排版，也不表示目前程式一定能正確合併所有情況。

- 書卷背景較接近一般文章段落；查經註釋多半是清單。
- 可能出現的清單標記包括 `零、壹、貳…`、`一、二、三…`、`1、2、3…`、`●`、`◎`、`☆`、`○`。
- 實際支援哪些標記、如何判定層級，以程式碼為準。
- 少數內容包含表格，例如列王記上背景。須特別查明表格如何避免被一般空白或清單處理破壞。

## 2.4 Strong Number（SN）

內容可能包含原文編號，例如馬太福音 1:1 的片段：

```text
●「基督」：SNG05547，「受膏者」之意，等同於希伯來文「彌賽亞SNH04899」。
```

- 依上述字串，`SNG05547` 表示 Greek Strong Number 5547，`SNH04899` 表示 Hebrew Strong Number 4899。
- 原稿解說曾寫作 `SNG05447 / 5447` 與 `SNG04899 / Hebrew`；本文件依原稿引用字串修正，使範例內部一致，並非另行驗證 API 或詞典內容。
- 新約註釋也可能同時出現希臘文與希伯來文 SN，不能僅依目前書卷的新舊約別推定所有 SN 的語言。

## 2.5 交互參照／經文參照

內容可能包含以下形式：

```text
壹、序言：君王的誕生 #1:1-2:23|\r\n  一、耶穌的家譜 #1:1-17|\r\n      ○#路 3:23-38|
#代上 3:17-19;申 25:5-10|
```

- 信望愛有既定格式，查證來源：[格式說明](https://bible.fhl.net/new/allreadme.html)。
- 參照可能省略書卷或章，需要上下文補足。使用者理解為使用目前 address 的書卷或章；實際上下文來源與繼承規則須查程式碼。
- 例如在馬太福音 1:1 的註釋中，`#1:1-17|` 指馬太福音 1:1–17。
- 混合參照例 `#1:1;路3:23|` 的語意是馬太福音 1:1 與路加福音 3:23。原稿此例缺少結尾 `|`，本文件補齊為與其他範例一致的形式；不代表已確認解析器如何處理缺少結尾的輸入。
- 點擊參照的使用者行為集中於第 7 節。

# 3. 使用者相對確定的程式資訊

以下僅為優先調查線索，仍需以 caller、callee、import 與事件路徑驗證。

- 註釋顯示核心是 `comment_render_async()`。
- `index/comment_render_es2023.js` 內有註解描述輸出的 HTML 結構，原稿定位約為第 69–84 行。
- `FhlInfoContent` 使用 singleton 模式，負責輔助資料內容；不僅處理註釋，也處理 parsing、講道錄音、串珠、典藏等。其 `render` 的 switch case 是辨識分支的線索。
- `FhlInfo` 與 `FhlInfoTitle` 也以 singleton 模式維護。使用者理解 `FhlInfo` 管理內容與標題，與其他區塊的互動主要透過 `FhlInfo.s.render`；`FhlInfoTitle` 負責分頁標題。
- `FhlInfoTitle` 的 `setTitleViaGb` 是分頁與繁簡文字的線索，原稿定位約為第 93–103 行。
- 相關 class 通常有 `init`、`render`、`registerEvents` 三類主函式；不可因此假定所有 class 都相同。
- 搜尋 `FhlInfo.s.render` 與 `FhlInfoContent.s.render` 可找更新觸發者，但必須再確認呼叫時是否真的進入註釋分支。

# 7. 已知使用者操作流程

以下都是使用者描述的既有行為，請逐項驗證；不應直接當成重寫需求或已確認規格。

## 7.1 閱讀經文並顯示註釋

1. 使用者閱讀經文，例如點擊猶大書 1:1。
2. 目前選取的經文位置改變。
3. 註釋顯示區取得該位置對應的內容，經轉換後顯示。

待查：初始化、開啟註釋分頁與切換經節的觸發關係，以及非註釋分頁時是否會取得或更新註釋。

## 7.2 點擊 SN 或經文參照

- SN：開啟 SN 字典。
- 經文參照：依設定，可能直接跳至章節、以彈出方塊顯示經文，或先提供這兩種選項。
- 本次追到設定判斷、參數與交接介面即可；不展開字典或經文彈窗的完整內部實作。

## 7.3 前一段／後一段

以目前註釋為猶大書 1:3–4 為例：前一段是 1:1–2，後一段是 1:5–7。

| 目前位置 | 操作 | 使用者描述的結果 |
| --- | --- | --- |
| 一般註釋段落 | 前一段／後一段 | 顯示相鄰註釋段落 |
| 書卷第一段 | 前一段 | 顯示書卷背景 |
| 書卷背景 | 前一段或後一段 | 回到書卷第一段 |
| 書卷最後一段 | 後一段 | 無效果 |

待查：前後段位置由 API 回傳還是前端計算；是否同步變動主經文選取、URL 或其他狀態。

## 7.4 書卷背景與返回

1. 在任意註釋段落按「書卷背景」，顯示該書卷背景。
2. 在背景按「上一段」或「下一段」，回到該書卷第一段。
3. 在背景按「返回」，回到開啟背景前的註釋段落。

「返回」與「前後段」的結果不同，須分開追蹤；不要假定它是瀏覽器上一頁。

# AI 分析要求

依 A–H 順序調查，以實際程式碼為主要依據。遇到本文件與程式碼衝突，並列使用者描述、程式證據及差異，不能默默選一邊或修改程式使其符合描述。

## A. 找入口

確認 UI event、初始化、route（若有）、function 或 class 的實際入口；驗證已提供的線索，補出其他與註釋直接相關的入口。證明如何進入註釋分支，不只找到共用 render 呼叫。

## B. 向下追蹤 Call Flow

由入口追到資料取得、轉換與顯示，用箭頭或樹狀流程表示，每一步說明做什麼，不只列函式名稱。若不同入口走不同路徑，分開描述。

## C. 向上追蹤 Caller

對重要函式查 caller，確認使用者操作、經文切換、初始化與其他功能間接呼叫的條件；並追查 import、載入與事件註冊，避免把未接入的實作當成現行流程。

## D. Data Flow

追蹤目前經文位置 → API 參數 → 回應欄位 → 解析／中間結構 → HTML／DOM。列出重要參數與回傳值、global／module state、class property、event payload，以及實際涉及的 localStorage、IndexedDB 或 cache；不存在或找不到時不要補造。

特別分開記錄聖經書卷編號、API 註釋書代號、查詢位置、回傳範圍、參照解析上下文與背景返回位置。

## E. State 與 Side Effects

列出重要狀態的讀取者、寫入者、用途與存續範圍，包含目前經節、所選分頁、背景返回位置及繁簡／參照行為設定等實際存在的狀態。指出 DOM、URL、儲存、全域物件、事件與非同步請求的副作用。

## F. UI 更新

分開定位資料取得、資料轉換、HTML／DOM 產生、UI 寫入與 event binding。確認重繪後事件如何接回，以及畫面結構註解是否仍符合實際輸出。

## G. 外部依賴

列出實際使用的 API、static files、library、shared module、global variable、browser API；若涉及 database，也需有證據。API 文件／回應觀察與前端程式證據應分別註明，單筆範例不可直接概括成所有資料的規則。無法讀取外部來源時寫明限制。

## H. 可能的 Dead Code

對相關實作標示「明確在 runtime path 中／可能仍使用／可能是 dead code／無法確認」，附上 caller、import、載入或事件路徑證據。沒有搜尋到直接 caller，不足以證明未使用；留意動態載入與事件間接呼叫。證據不足不要建議刪除。

# 證據可信度

分析報告中的技術結論分為：

- **Confirmed**：有明確程式碼證據，附檔案、實際行號與符號。若另有執行觀察，明示觀察方式；僅靜態追蹤不能宣稱已實測。
- **Inferred**：依結構合理推論但證據鏈不完整，說明推論依據與缺少哪一段證據。
- **Unknown**：目前無法確認，說明已查位置、缺少資訊或驗證限制。

使用者提供的資訊不能單靠本文件升級為 Confirmed。不要把 Inferred 寫成 Confirmed，也不要把示例行為寫成既有功能。程式碼註解若與執行內容不同，須註明差異。

# 最終輸出格式

產出一份獨立的繁體中文分析報告，包含以下 10 節。報告開頭記錄分析時的版本（例如 commit 與工作目錄是否有相關未提交變更）、分析範圍、驗證方式與限制，以便後續 session 理解證據時效。

1. **功能摘要**：功能目的、使用者如何操作、系統如何完成。
2. **Entry Points**：主要入口、來源、觸發條件與證據。
3. **Runtime Flow**：用簡單樹狀或箭頭表示主要及必要分支流程，說明每一步的作用。
4. **Data Flow**：重要輸入、API 欄位、中間結構、轉換步驟與輸出；詳述純文字解析的關鍵規則。
5. **State / Side Effects**：重要狀態、讀寫位置、修改條件與副作用。
6. **Important Business / Behavior Rules**：只列程式碼可證實的行為規則與邊界條件；對照第 7 節，指出與使用者記憶的差異。未知行為移至第 9 節。
7. **Important Files / Functions**：只列理解功能必要的核心程式與責任，不堆列所有搜尋結果。
8. **Dead / Legacy Code Candidates**：分成「高度可能已未使用／可疑／無法確認」，附理由；沒有候選就明確寫無。
9. **Confirmed / Inferred / Unknown**：集中整理可信度、使用者資訊與實作差異，以及仍需確認的事項。
10. **Recovered Feature Specification**：以 Input、Behavior、Output 及必要邊界條件描述目前系統做什麼，不依賴函式或 class 名稱。只納入已確認行為，附規則對應的報告證據位置；尚未確認的部分明列為規格缺口，不補成要求。

這份輸出描述「現行功能」，不是「建議的新功能」。若沒有證據，直接寫「目前無法確認」。不要因為某種設計看起來合理，就假定原系統如此；也不要因為舊程式不好看就認定它是錯的。
