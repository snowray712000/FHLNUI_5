# SN 全為 0 時（如 WH00）去除前導 0 的 bug 修正

日期：2026-09-20

## 背景

`FhlLecture.es2023.js` 在顯示經文時，會將原文帶有 Strong's Number 的標記（例如
`<WH0559>`）拆解成 `.sn-text` / `.sn` 的 span，並在過程中把 SN 前面多餘的 `0`
去掉（例如 `0408` → `408`）。

使用者發現少數經文會出現 `WH00` 這種全部是 `0` 的 SN 標記，懷疑這種情況去除
前導 0 後，SN 會被誤判為空字串，而非正確的 `"0"`。

## 調查

- 經文顯示的主要拆解流程是
  [`FhlLecture_render_mode_common_es2023.js`](../index/lecture/FhlLecture_render_mode_common_es2023.js)
  中的 `do_sn()`（被 `FhlLecture_render_core.js` 的 `parseBibleText` 呼叫）。
  其去除前導 0 的寫法是：

  ```js
  let sn = parseInt(sSN).toString() + (sA == 'a' ? sA : '')
  ```

  這裡用 `parseInt` 轉成數字再轉回字串，`"00"` 會被正確轉成 `"0"`，
  **不會**變成空字串，因此這個主要顯示流程本身沒有問題。

- 但專案中另外有 3 處用「字串正則替換」`sn.replace(/^0+/, '')` 的方式去除
  前導 0，這種寫法在輸入全部是 `0`（例如 `"00"`）時，替換後會得到空字串
  而非 `"0"`，是同一類型的 bug：

  | 位置 | 修正前 | 用途 |
  |---|---|---|
  | [`cvt_others.js:410`](../index/cvt_others.js) | `sn.replace(/^0+/, '').toLocaleLowerCase()` | 原文匯編 / 註解等內容的 DOM tagName 解析 |
  | [`parsing_gen_prompt_parsing_table_es2023.js:6`](../index/parsing_gen_prompt_parsing_table_es2023.js) | `return sn.replace(/^0+/, '')` | 產生給 AI 的 parsing table prompt |
  | [`parsing_render_bottom_table.es2023.js:188`](../index/parsing_render_bottom_table.es2023.js) | `return sn.replace(/^0+/, '')` | Parsing 對照表下方表格渲染 |

  作為對照，`FhlLecture.es2023.js` 的 1487、1493 行其實已經有正確的防護寫法：

  ```js
  re_parsing.record[i].sn = element.sn.replace(/^0*/, '') || "0" // "00000" 遇到，就會變成 "0"
  ```

## 修正內容

將上述 3 處都補上 `|| "0"` 的防護，讓全 0 的 SN 正確轉成 `"0"`，而非空字串，
寫法與 `FhlLecture.es2023.js` 既有的防護一致：

```js
// cvt_others.js
sn = (sn.replace(/^0+/, '') || "0").toLocaleLowerCase();

// parsing_gen_prompt_parsing_table_es2023.js
// parsing_render_bottom_table.es2023.js
return sn.replace(/^0+/, '') || "0"
```

## 結論

- 經文主要顯示流程（`do_sn`）本身沒有這個 bug，因為用 `parseInt` 處理。
- 但其他 3 個同樣需要去除 SN 前導 0 的地方使用字串正則替換，遇到全 0 的 SN
  （如 `WH00`）會產生空字串，已一併修正，避免後續查表、顯示或送給 AI 的
  prompt 中出現錯誤的空 SN 值。
