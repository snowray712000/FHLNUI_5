# 典藏（ob）已證實 bug 修正規格

承接自：[`0920a_典藏_ver3.md`](0920a_典藏_ver3.md)（逆向分析報告，下稱「逆向報告」）第 6、9 節列出的已證實程式缺陷。
目的：另一個工作階段（session）要在**本專案（舊版，仍在線上使用中）**修正這些 bug，本文件給那個 session
當修正依據，不含新功能、不含架構重寫，只修 4 項已證實缺陷。修正後應更新逆向報告或另立驗證記錄，但那是
修正 session 自己的事，不在本文件範圍內。

修正原則：**最小改動**，只動被證實有問題的那幾行／那個範圍，不要順手重構週邊 React/jQuery 寫法。改完每一項
後應能用本文件列出的實測案例手動或用瀏覽器 console 驗證。

## 1. 節號範圍文字組字錯誤（`res += ... this.props.isgb? "节": "節"` 缺括號）

**位置**：`static/ob_api/obphp.js:351-366`（`content.render` 內組 `rtitle4` 的區塊）。

**現行程式**（節錄，行號為本檔目前行號）：

```js
// obphp.js:351-366
var res = "";
if (re_record.vid != 0) // 封面的 vid = 0 時, chap sec 屬性都不值得參考
{
  if (re_record.bchap != 0) {
    res += re_record.bchap.toString() + "章";
    if (re_record.bsec != 0)
      res += re_record.bsec.toString() + this.props.isgb? "节": "節";
    res += "至";
  }
  if (re_record.echap != 0) {
    res += re_record.echap.toString() + "章";
    if (re_record.esec != 0)
      res += re_record.esec.toString() + this.props.isgb ? "节" : "節";
  }
}
```

**問題**：JS 三元運算子 `?:` 優先權低於 `+`，因此
`res += re_record.bsec.toString() + this.props.isgb ? "节" : "節"`
會先算完 `res += (re_record.bsec.toString() + this.props.isgb)`（字串 `+` boolean，`bsec` 被轉成字串後
直接跟 `isgb` 串接成類似 `"2false"` 這種怪字串），再對這整個 `+=` 表達式的結果值做三元判斷（永遠是
truthy 字串），但因為 `?:` 不在括號內，真正被丟進 `res +=` 的只有前半段 `bsec.toString() + isgb`，後面的
`? "节" : "節"` 只是被求值但結果被捨棄，等同於白算。**節號本身沒有正確接進 `res`，且會混入布林轉字串的雜訊**。

**實測樣本**（逆向報告 6.1、8 節）：`re_record = {bchap:1, bsec:2, echap:1, esec:5, vid:非0}`，`isgb=false` 時，
`render` 應顯示「1章2節至1章5節」，實際結果為「1章至1章」（節號整個消失，且原始行為其實是把
`"2" + false` 這種字串塞進去又被捨棄，不是簡單的「沒加括號」，要注意 `bsec.toString() + this.props.isgb`
本身也是無意義運算，不只是三元運算子優先權問題）。

**修正方式**：把三元運算子整個包進括號，讓字串串接的對象是三元運算子的**結果**而不是條件判斷式的一部分：

```js
if (re_record.bsec != 0)
  res += re_record.bsec.toString() + (this.props.isgb ? "节" : "節");
```

```js
if (re_record.esec != 0)
  res += re_record.esec.toString() + (this.props.isgb ? "节" : "節");
```

只需要在這兩行各加一組括號（`:355`、`:361` 附近，實際行號以修正時的檔案為準，用上面貼的程式片段比對
定位），不需要動其餘邏輯。

**驗證**：呼叫 `https://bible.fhl.net/json/sob.php?gb=0&book=27&engs=Gen&chap=1&sec=1`（逆向報告 4.3 節已知
回應 `bchap=echap=1, bsec=esec=0`，這筆剛好 `bsec/esec` 都是 0 不會觸發原本的 bug，不能拿來當回歸案例）；
需要另外找一筆 `bsec`/`esec` 非 0 的典藏書實測（逆向報告未列出這樣的樣本，需要修正時自行用 `sob.php`
找一筆 `bsec!=0` 或 `esec!=0` 的紀錄，或直接手動建構假資料丟進 `content.render` 驗證字串組出來是否為
「N章M節至...」的正確格式）。

## 2. `sob.php` 回應非合法 JSON 時 `JSON.parse` 無防護

**位置**：`static/ob_api/obphp.js:546`（`_set_obdata_from_ajax` 查 `ob.php`）、`:562`（同函式內查
`sob.php?book=all`）、`:673`（`_query_sob_from_ajax_book_chap_sec`）、`:706`（`_query_sob_from_ajax_idxbook`）、
`:737`（`_query_sob_from_ajax_page`）共 5 處，皆是 `var juc = JSON.parse(jstr)` 這個寫法，前後都沒有
`try/catch`。

**問題**：逆向報告 4.3 節已用 PowerShell 實測 `sob.php?gb=0&book=27&page=15`／`page=16`
（超過 `total` 頁數的邊界請求）：HTTP 狀態碼是 200，但回應 body 在 `record` 陣列起始位置被插入一段非法
文字 `Page number too large 15`／`16`，導致整個 body 不是合法 JSON。`JSON.parse` 在這種輸入上會直接
`throw SyntaxError`，因為外層 `fhl.json_api_text` 的 ajax success callback 沒有 try/catch，這個例外會
一路往上炸穿，使用者翻頁翻到底時整個典藏元件可能卡住或整頁 JS 報錯（實際使用者可見結果逆向報告列為
Inferred，未在瀏覽器實測，但 body 非法 JSON 這件事本身是 Confirmed / A）。

**修正方式**：5 處 `JSON.parse(jstr)` 都比照下列寫法加 try/catch，失敗時走既有的「失敗處理」分支（各處
原本 error callback 已有 `pthis.setState({ err_msg: ... })` 的既有寫法可以直接沿用，不用新增 UI）：

```js
var juc;
try {
  juc = JSON.parse(jstr);
} catch (e) {
  pthis.setState({ err_msg: "sob.php 回應格式錯誤" }); // 或依原本該處的既有錯誤訊息文字
  return;
}
if (juc.status == "success") {
  // ...原有邏輯不動
}
```

五個位置分別是（訊息文字沿用各自原本 error callback 已在用的字串，維持一致）：

- `:546`（`ob.php`）：原 error 分支文字是 `"ob.php錯誤"`（`:617`）。
- `:562`（`sob.php?book=all`）：原 error 分支文字是 `"sob.php book=all 錯誤"`（`:599`）。
- `:673`／`:706`／`:737`（`sob.php` 單書/翻頁三個查詢函式）：原 error 分支文字都是 `"sob.php錯誤"`。

**注意**：`:562` 那個 callback 巢狀在 `:546` 的 success 分支裡（查完 `ob.php` 成功後才查
`sob.php?book=all`），兩層都要各自加 try/catch，不能只加外層。

**驗證**：用逆向報告 4.3 節記錄的 `sob.php?gb=0&book=27&page=15` 或 `page=16` 實際呼叫（回應非法 JSON），
確認修正後 `err_msg` 被正確設定、不再有未捕捉例外（瀏覽器 console 應無 Uncaught SyntaxError）。也要確認
正常回應（例如 `page=14`）行為不變。

## 3. 多次請求無序保護（晚到的舊回應覆蓋新選擇，含 `idxbook1` 殘留欄位）

**位置**：`static/ob_api/obphp.js:427-432`（`_set_book_id`）、`:687-719`（`_query_sob_from_ajax_idxbook`）。

**現行程式**：

```js
// obphp.js:427-432
_set_book_id: function (idxbook1) {
  this.setState({ idxbook: idxbook1 });
  this._query_sob_from_ajax_idxbook(idxbook1);
},
```

```js
// obphp.js:687-719（節錄關鍵行）
_query_sob_from_ajax_idxbook: function (idxbook1) {
  var idxbook = idxbook1;
  // ...組 url...
  var pthis = this;
  fhl.json_api_text(url, function (jstr, pthis) {
    var juc = JSON.parse(jstr);
    if (juc.status == "success") {
      pthis.setState({
        idxbook, idxbook1,      // :711，物件簡寫同時寫入 idxbook 與 idxbook1 兩個 state 欄位
        sobdata: juc.record,
        err_msg: ""
      });
    }
  }, function (msg, pthis) {
    pthis.setState({ err_msg: "sob.php錯誤" });
  }, this, true);
},
```

**問題**：

1. **競速（race）**：使用者連續點兩列「閱讀」（例如先點 id=27 再點 id=257）時，會依序發出兩個
   `sob.php` 請求。若先送出的（27）比後送出的（257）晚回應（伺服器端延遲、網路排隊等常見情境），
   callback 執行順序會是「257 先回、27 後回」，最後 `setState` 寫入的是**舊選擇**（27）的
   `idxbook`/`sobdata`，使用者畫面上會顯示他點的第二本書（257）的短暫閃現後，被第一本書（27）的舊資料
   蓋掉，等同於「選擇被往回倒退」。這是純粹的 callback 完成順序問題，程式本身完全沒有 request
   id／序號／取消機制去比對「這個回應是不是最新那次請求的」。
2. **殘留欄位 `idxbook1`**：`:711` 用物件簡寫 `{ idxbook, idxbook1, ... }` 同時把兩個 key 塞進
   state，但 `idxbook1` 只是函式參數名稱，不是刻意要保留的欄位，目前找不到任何地方讀取
   `state.idxbook1`，是無用途的殘留寫入，會讓 React state 多一個沒人用的欄位。

**修正方式**：在 `frame` 元件內加一個遞增的請求序號（例如加到 `getInitialState` 回傳的物件裡，
`obreqSeq: 0`），每次發出 `_query_sob_from_ajax_idxbook`／`_query_sob_from_ajax_book_chap_sec`／
`_query_sob_from_ajax_page` 前遞增並記住「這次是第幾號請求」，callback 裡先比對目前
`this.state.obreqSeq` 是不是等於發出當下記下來的號碼，不等就直接 return（代表已經有更新的請求發出過，
這次回應是過期的，不寫入 state）：

```js
_query_sob_from_ajax_idxbook: function (idxbook1) {
  var idxbook = idxbook1;
  var mySeq = ++this.state.obreqSeq; // 或用 this.setState 遞增後再讀，依現有 setState 慣例調整
  // ...組 url...
  var pthis = this;
  fhl.json_api_text(url, function (jstr, pthis) {
    if (pthis.state.obreqSeq !== mySeq) return; // 過期回應，忽略
    var juc;
    try { juc = JSON.parse(jstr); } catch (e) { pthis.setState({ err_msg: "sob.php 回應格式錯誤" }); return; }
    if (juc.status == "success") {
      pthis.setState({
        idxbook,
        sobdata: juc.record,
        err_msg: ""
      });
    }
  }, function (msg, pthis) {
    if (pthis.state.obreqSeq !== mySeq) return;
    pthis.setState({ err_msg: "sob.php錯誤" });
  }, this, true);
},
```

同時把 `:711` 的 `idxbook, idxbook1,` 改成只留 `idxbook,`，移除無用途的 `idxbook1` 欄位寫入。

**範圍提醒**：`_query_sob_from_ajax_book_chap_sec`（`:652-686`）與 `_query_sob_from_ajax_page`
（`:733-750` 附近）兩個函式也有同樣「沒有序號保護」的問題，且都會寫 `sobdata`，建議三個查詢函式共用
同一個 `obreqSeq` state（同一個 frame 元件內任何一種查詢都算「最新操作」，不需要三個查詢各自獨立計數）。
不確定的地方：`componentWillReceiveProps`（`:479-481`）觸發的查詢跟使用者手動點擊觸發的查詢是否該共用
同一個序號空間——本文件建議共用（比照上面「同一個 frame 元件內任何查詢都算最新操作」的原則），修正
時如果覺得需要分開處理，请自行判斷並在修正記錄裡寫清楚理由。

**驗證**：手動測試較難重現真實網路的回應倒序，建議修正後用瀏覽器 devtools 的 Network throttling／或暫時
在其中一個 callback 前手動加 `setTimeout` 延遲，模擬「先點的請求後回應」情境，確認畫面最終停留在**後點的
那本書**，不會被先點的舊回應覆蓋。另外確認 `state.idxbook1` 已不存在（React devtools 檢查 state）。

## 4. React 重複初始化多查一次頁

**位置**：`index/FhlInfo.es2023.js:14-23`（`FhlInfo.init`）、`index/FhlInfoContent.es2023.js:196-229`
（`FhlInfoContent.render`，內含 `case "fhlInfoOb"` 分支，第 218-227 行左右組 `rProp` 並呼叫
`React.render`）。

**現行程式**（節錄）：

```js
// index/FhlInfo.es2023.js:14-23
init(ps) {
    const rfhlmap = window.rfhlmap
    FhlInfoTitle.s.init(ps, $('#fhlInfoTitle'));
    FhlInfoTitle.s.registerEvents(ps);
    FhlInfoContent.s.init(ps, $('#fhlInfoContent'));   // 內部會自行 render 一次
    FhlInfoContent.s.registerEvents(ps);
    ParsingPopUp.s.init(ps, $('#parsingPopUp'));
    this.registerEvents();
    this.render(ps);                                    // 又呼叫一次 render
    // ...
}
```

**問題**：`FhlInfoContent.s.init(ps, ...)` 內部本身就會呼叫一次 render（逆向報告 3 節 Runtime Flow 已確認
「內容 `init` 立即 render」），緊接著 `FhlInfo.init` 自己又呼叫 `this.render(ps)`，等於**同一次頁面初始化
流程觸發兩次 `FhlInfoContent.render`**。若初始化時 `ps.titleId` 剛好是 `"fhlInfoOb"`（使用者上次關閉頁面
時面板停在典藏分頁，見逆向報告「網頁初始化／恢復面板」一列），會建立兩次 `React.render(frame, dom2)`：
第一次建立全新 `frame`（`componentWillMount` 觸發 `_set_obdata_from_ajax`，發一次 `ob.php`+`sob.php`
請求），React 判斷 `dom2` 容器已有相同型別的元素時，第二次 `React.render` 會重用同一個 `frame`
實例並走 `componentWillReceiveProps`（即使 `nextProps` 的經節跟目前完全相同，也會**無條件**再發一次
`sob.php` 單書查詢，見逆向報告 3 節「Confirmed / S+E」段落）。結果是**頁面剛載入、還原到典藏分頁時，
比正常情境多發一次不必要的 `sob.php` 請求**。

**修正方式**：本項是「初始化流程呼叫了兩次 render」的架構性重複，不是單一行程式碼的筆誤，建議兩種方向
擇一，由修正時視風險自行決定（本文件不代為決定，因為牽涉 `FhlInfoContent.init`／`FhlInfo.init` 對其他
分頁的行為，需要一併確認別的分頁沒有依賴「`init` 內部先 render 一次」這個副作用）：

1. **移除 `FhlInfo.init` 最後的 `this.render(ps)`**，若 `FhlInfoContent.s.init` 內部已保證第一次呈現
   正確——前提是需要確認 `FhlInfoTitle.s.init`／`ParsingPopUp.s.init` 不依賴 `FhlInfo.render` 這次呼叫
   才能正確初始化（目前看起來 `FhlInfoTitle`/`ParsingPopUp` 各自有自己的 `init`，`FhlInfo.render` 呼叫的
   應該只有 `FhlInfoContent` 那份，但需要修正時重新確認一次 `FhlInfo.render` 的實際內容，本報告未附上
   `FhlInfo.render` 的程式碼）。
2. **保留兩次呼叫的呼叫點，但在 `frame.componentWillReceiveProps`（`obphp.js:479-481`）內比較
   `nextProps` 的 `ibook`/`ichap`/`isec`/`isgb` 是否跟 `this.props` 完全相同，相同就不重新查詢**：

   ```js
   componentWillReceiveProps: function (nextProps) {
     if (nextProps.ibook === this.props.ibook &&
         nextProps.ichap === this.props.ichap &&
         nextProps.isec === this.props.isec &&
         nextProps.isgb === this.props.isgb) {
       return; // 經節與語系都沒變，不重新查詢
     }
     this._query_sob_from_ajax_book_chap_sec(nextProps.ibook, nextProps.ichap, nextProps.isec);
   },
   ```

   這個方向影響範圍較小（只動 `obphp.js` 一處），且對「正常情境下經節真的改變才查詢」這個語意更正確，
   本文件**建議優先採用方向 2**，除非修正時發現方向 1 更適合整體架構。

**驗證**：清空瀏覽器 localStorage 中的面板狀態、手動設成典藏分頁（依 `TPPageState.saveToLocalStorage`
儲存格式，或直接在該次 session 走一次「切到典藏分頁」再重新整理頁面），用 Network 面板確認頁面載入時
`sob.php`（單書查詢）只發出一次，不是兩次。

## 5. 修正順序建議

四項互相獨立，沒有相依關係，可以任意順序修正、各自獨立驗證、各自獨立提交。若要排序，建議：
第 1 項（純文字組字，風險最低）→ 第 2 項（加 try/catch，風險低）→ 第 3 項（改 state 結構，風險中，需要
實際測試競速情境）→ 第 4 項（跨兩個檔案的初始化流程調整，風險最高，需要確認不影響其他分頁初始化）。
