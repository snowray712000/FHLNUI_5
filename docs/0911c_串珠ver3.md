分析日期：2026-09-11（Asia/Taipei）。版本：`612abec9447936d2105eb2af997c80b920f08ab5`。分析開始時 `git status --short` 無輸出。本文依 `docs/0911b_串珠ver2.md` 的分析要求及十節格式撰寫；使用者已確認目標是串珠而非註釋，並指定本報告檔名。本次只新增報告，未修改程式、既有測試或前兩版文件，未進行重構設計。

證據記法：`專案相對路徑:行號` 後附函式／事件；行號以本次 checkout 為準。**Confirmed** 表示有程式碼證據，若附「執行」則另有本次執行結果；不等於已在完整瀏覽器 UI 驗收。**Inferred** 為條件式推論；**Unknown** 為尚無充分證據。使用者記憶、註解與背景文件均不獨立作為 Confirmed 依據。

驗證方式：追蹤主頁 import、caller、callee、事件與讀寫；以 Node.js 24.12.0 和真正的 QUnit 2.24.1 執行現有三組 TSK 測試；另以一次性命令呼叫現有函式觀察邊界輸出，未新增測試檔。線上 API 文件可讀，但六個資料請求均遭 HTTP 403；未取得真實 `sc.php` JSON。未啟動完整主頁／人工展示頁，未做瀏覽器 DOM、點擊、畫面及競速實測。詳細結果與重現方法在第 9 節。

## 1. 功能摘要

**Confirmed**：串珠分頁讀取目前聖經書卷、章、節，向 `sc.php` 指定資料來源 `book=4` 取得文字，整理成「本章總覽」「本節相關」及關鍵字段落，顯示交互參照與從部分說明文字抽出的 SN。上下各有前、後、標題工具列。主路徑是 `index/FhlInfoContent.es2023.js:211` 的 `fhlInfoTsk` 分支 → `index/tsks/renderTsk.js:156` 的 `renderTsk()`。

**Confirmed**：這不是全文翻譯。顯示模式主要轉換參照的英文短書名；摘要說明、關鍵字及一般英文文字不經翻譯。點擊資料與畫面文字分開存放。前後切換也不是前端自行加減一節，而是使用 API 提供的地址。證據：`index/tsks/renderTsk.js:26,106,156`。

本次最重要的行為差異：

- **Confirmed**：新主流程與舊 React 流程並存，字級工具仍可呼叫舊版，不能把 `index/renderTsk.es2023.js` 當作 dead code（第 8 節）。
- **Confirmed**：TSK 前後按鈕改全域地址但只重繪串珠；不主動同步主經文、書卷選擇器、歷史或 URL（第 5、6 節）。
- **Confirmed**：顯示模式預設與設定 UI fallback 不一致，選擇模式後只儲存、不立即重新 render（第 6 節）。
- **Confirmed**：SN 產生 H、G 兩個候選，而字典點擊依賴共用容器曾由註釋模組綁定事件，不能宣告所有啟動順序都可用（第 6 節）。
- **Confirmed（執行）**：「本節相關」參照有重複／多餘書名的轉換案例；共用方法 2 取不到第一個地址（第 4 節）。

## 3. Runtime Flow

以下為 **Confirmed** 的新主路徑，括號說明每一步工作：

```text
分頁 click／已選 TSK 時的內容刷新
└─ FhlInfoContent.render（titleId == fhlInfoTsk）
   └─ tsks/renderTsk()（不接收 caller 的 ps）
      ├─ api_tsk()
      │  ├─ 讀 TPPageState.s 的 bookIndex/chap/sec/gb
      │  ├─ gen_tsk_url（標準英文書名，sc.php book=4）
      │  └─ fetch → response.text（未檢查 HTTP ok）
      ├─ JSON.parse（未 catch）
      ├─ normalize_sc_result（就地轉 prev/next 書名為書卷 id）
      ├─ record[0].com_text，缺省用空字串
      ├─ 再讀當下 TPPageState.s 地址
      ├─ parseTsk（分 block、inline、摘要範圍、特殊字眼）
      ├─ cvt_tsk_blocks_to_dtexts（摘要／本節相關／關鍵字重組）
      ├─ 遞迴轉參照描述及顯示書名（兩者規則不同）
      ├─ dtexts_render（DText → jQuery DOM）
      └─ 清空 #fhlInfoContent 子內容
         ├─ 上工具列
         ├─ .tsk_content 與產生的 DOM
         └─ 下工具列；同時填入前後地址及標題

工具列前／後 click
└─ DOM book/chap/sec → parseInt → 全域地址 → renderTsk()

參照 click（容器委派）
└─ addr-data / addr-desc + version[0] + bookDefault + 原事件
   └─ queryReferenceAndShowAtDialogAsync
      ├─ method 0：選擇方法的小對話框
      ├─ method 1：qsb 查詢 → 經文對話框
      └─ method 2：第一個地址 → 主經文等重繪
```

## 4. Data Flow

### 4.1 地址、API 與正規化

**Confirmed**：前端書卷 `bookIndex` 是 1-based；`gen_tsk_url` 用 `getBookNameArrayEnglishNormal()[book-1]` 取得 `Gen` 等標準英文名稱。查詢為 `sc.php?book=4&engs=…&chap=…&sec=…&gb=…`，`book=4` 是資料來源，不是聖經第四卷。一般環境用同源 `/json`；`isRDLocation()` 判定 localhost、127.0.0.1 或指定 file origin 時用 `http://127.0.0.1:15600/json`。主流程實際傳 `[bookIndex,chap,sec]`；URL helper 的物件地址 fallback 並不會補救陣列內的 NaN。證據：`index/tsks/renderTsk.js:51–81`；`index/isRDLocation.es2023.js:6`；`index/BibleConstantHelper.es2023.js:142–150`。

官方 [JSON API 文件](https://bible.fhl.net/json/) 的 `sc.php` 段落說明 `book/engs/chap/sec/gb`、`title/book_name/com_text` 與 `prev/next`；稱後兩者為前後一段，不保證數值加減一。這是介面文件，不能代替本次未取得的實際回應。

`normalize_sc_result`（`index/api/sc.js:9–40`）的實際契約：

- 僅 `status == 'success'` 才正規化，否則原樣返回；不驗證 `record_count`。
- 先從 `prev.book || next.book || 0` 保存來源編號為 `sc_book`，從首筆記錄取 `sc_book_name`。
- 將 `prev/next.engs.toLowerCase()` 交給 `getBookId`，覆寫 `.book`，刪除 `.engs`；保留其章節欄位。刪除首筆 `book_name`，修改的是原物件，不是複本。
- 缺少 prev/next 本身可跳過；存在物件但缺 `.engs` 則可能拋 TypeError。`getBookId` 查不到回 `-1`（`index/BibleConstantHelper.es2023.js:30–33`），此處未拒絕。
- `null` JSON 會在讀 `joResult.status` 失敗。不能把所有「無效回應」等同「無資料」。

### 4.3 參照補全及已重現的差異

**Confirmed**：parser 的 `addRefProp` 使用英文短名陣列（TSK 的 `Ge/Le/Nu` 等）辨識第一個分號片段：無卷無冒號，補目前卷、章；有章無卷，補目前卷；已有卷則保留。只對 `ref` 移除 `*marg:`（不分大小寫），`w` 保留它。它不把全部地址展開，也不逐一驗證所有片段。證據：`index/tsks/parseTsk.js:269–306`、`index/BibleConstantHelper.es2023.js:149–150`。

下一階段 `normalize_ref_description` 取 `item.ref || item.w`。只在 `#…|` 形式上去除界符；陣列地址有效時，把每個「純節數」分號片段補上**目前章**。`note/refOnly` 使用預設 `prependBookAbbr=true`，不管內容是否已有卷都再加目前短書名；keyword 分支明確傳 false。證據：`index/tsks/cvt_tsk_blocks_to_dtexts.js:18–55,106–123,159–203,254–269`。

本次直接執行原函式（合成輸入，非 API 樣本）：

| 輸入（目前地址） | parser 的 ref | DText 的 refDescription | 結果 |
| --- | --- | --- | --- |
| `# 3|`（創20:7） | `# Ge 20:3|` | `Ge Ge 20:3` | 本節相關多加一次卷 |
| `# Job 26:7|`（創1:1） | `# Job 26:7|` | `Ge Job 26:7` | 已指定他卷仍加目前卷 |
| `* test\n# 3|`（創20:7） | `# Ge 20:3|` | `Ge 20:3` | keyword 不再 prepend |

前兩種描述經 `cvt_ref_to_chinese` 仍原樣保留，因整個候選書名 `Ge Ge`／`Ge Job` 不在對照表。接著實際執行 `splitReference` 得到：

```json
{"input":"Ge Ge 20:3","result":[{"w":"Ge "},{"w":"Ge 20:3","refAddresses":[{"book":1,"chap":20,"verse":3}]}]}
{"input":"Ge Job 26:7","result":[{"w":"Ge "},{"w":"Job 26:7","refAddresses":[{"book":18,"chap":26,"verse":7}]}]}
```

**Confirmed**：`get_first_addr` 只取 `splitResult?.[0]?.refAddresses?.[0]`，不搜尋後續節點，所以此處為 undefined；方法 2 的 `show_in_embed` 隨即讀 `.book`，此輸入會落入失敗條件。方法 1 仍將描述交給 qsb，後端如何解讀這兩字串為 **Unknown**，本次未查到真實 qsb 回應。證據：`index/queryReferenceAndShowAtDialogAsync.es2023.js:124–157,255–271`；`index/splitReference.es2023.js:16–45,88`。這些結果不表示所有參照都失敗，也不代表 32 個既有測試覆蓋了 parser→converter→互動的組合。

## 6. Important Business / Behavior Rules

### 6.1 分塊與摘要

以下規則皆為 **Confirmed**，證據是 `index/tsks/parseTsk.js`：

- `parseTsk(:19)` 非字串回空陣列；CRLF 正規化成 LF，以連續空行分塊、trim、移除空塊，再由 `splitKeywordBlocks(:96)` 把同塊內每個行首 `*` 加空白拆開。
- 分類順序：整塊恰為 `# n|` 且 n 等於數字型態 address.sec → empty；否則同形式為 refOnly；第一個展開後區塊以 `數字;` 開頭 → summary；以 `*` 加空白開頭 → keyword；含任何 `#…|` → refOnly；其餘 note。故 refOnly 仍可能夾一般文字，不一定是「純參照」。
- 摘要不檢查目前是否第一節；「只在第一節」不是前端限制。直接在創1:2 上解析 `1; first\n3; next` 仍得到 summary。
- `postProcessSummaryBlocks(:370)` 須有數字型態 book、chap 才把摘要行轉 summaryItem。每個 `n;文字` 開新項，其餘行延續上一項。結束節＝下一起點−1；最後一項取章節數 helper；無有效節數回自身起點，結束小於起點也夾回起點。不是單純顯示起點。
- 節數 helper 的真正契約為 1-based（`index/BibleConstantHelper.es2023.js:159–168`）。parser 還寫有第一次取不到時試 book−1 的 fallback；不能因註解把 helper 說成可能是 0-based。無地址時 summary 可能只有原 inline items，converter 不會把那些非 summaryItem 當摘要列顯示。

### 6.2 關鍵字、一般文字、參照

- **Confirmed**：keyword 第一行遇 `. Or,` 優先切分，keyword 保留句點；遇 `. Heb`／`. Gr` 切開且 keyword 不保留該句點；其他以第一行／後續行分界。不是語意分析 KJV，也未驗證每個 keyword 的來源。`index/tsks/parseTsk.js:329–360`。

- **Confirmed**：相鄰 ref（包括只隔空白者）合併，片段用分號串接；一般文字隔開則不合併。相同書名且後段確有章冒號時省略後續同書名；不是跨所有 block 共用一個參照狀態。`index/tsks/parseTsk.js:148–175,182–260`。

### 6.3 SN 與「文中特殊字眼」

## 10. Recovered Feature Specification

以下描述現行新串珠路徑可由證據支持的行為，而非理想設計。證據回指第2–6節；舊字級路徑的例外見第8節。

**功能：串珠（TSK）**

**Input**

- 使用者目前的聖經書卷、章、節。
- 繁簡設定及參照書名顯示模式：英文、中文縮寫、中文全名。
- 串珠服務回傳的首筆內容、標題及可選的前後地址。
- 點擊參照時所選的經文譯本與互動方法。

**Behavior**

1. 開啟串珠分頁時取得該地址內容。已在該分頁時再次點分頁不重新取得；經文選節、書卷／章選擇、部分歷史及共用導航入口刷新內容時，會重新取得串珠。並非任何地址修改都自動刷新；主經文前後章另有尚未確認的入口限制。
2. 支援將章總覽、節相關說明／參照、關鍵字段落分組顯示。總覽各項包含由下一起點推算的節範圍，最後項到已知章末。是否顯示總覽取決於內容格式，不限制只有第一節。
3. 保留一般說明及關鍵字的原文，不提供全文翻譯。參照書名可按模式轉中文；點擊描述與畫面文字分離，切換英文模式仍保留內部參照轉換。未辨識名稱可能原樣保留。
4. 部分文字中的 definition 數字會在補充列列出 H/G 兩個 SN 候選；部分 ver/ch/英文短書名參照亦可追加。這不是所有文字位置都偵測，也不保證每個數字對應的字典均有資料。SN 點擊是否接上字典還依賴頁面已建立的共用事件。
5. 點擊一般參照可依設定先詢問、顯示經文對話框，或跳到第一個參照地址並更新主經文等畫面。現有描述補全存在已重現的多餘書名前綴案例，故不保證所有參照都能成功跳轉。
6. 內容上下各提供前後按鈕，採服務回傳地址，不自行加減節數。它們改變目前全域地址並重新顯示串珠，但不主動同步主經文、歷史或網址。缺少方向地址時仍顯示可點按鈕，操作可能把地址變成無效值。
7. 標題按服務字串拆分後顯示；標題按鈕沒有已確認的動作。新串珠沒有已實作的背景、返回、說明或工具列設定操作。
8. 改顯示模式會儲存，下一次內容刷新才採用；設定面板對英文值有回顯全名的現行差異。繁簡切換會觸發內容重新取得，但固定中文文案並非全部轉換。
9. 可成功解析而沒有可顯示內容時顯示 `(本節無資料)`。請求或格式錯誤沒有專用錯誤提示／重試；先前畫面可能保留。快速切換沒有確保最新請求勝出的機制。

**Output**

- 含總覽、節相關及關鍵字內容的串珠區域，或無資料文字。
- 上下工具列與服務提供的標題片段。
- 符合條件的交互參照／SN 元素及其共用互動；上述已確認限制仍屬現行行為的一部分。

這份規格不把尚未取得的真實資料格式、後端地址邊界、字典領域判定或未執行的 UI 體驗補成保證。
