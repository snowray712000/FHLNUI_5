# 功能逆向分析

我要你針對既有專案中的一個功能，進行 **feature-by-feature reverse engineering（逐功能逆向分析）**。

目標不是重構程式碼，也不是提出新的架構，而是：

- 從現有程式碼反推出這個功能實際如何運作
- 找出它的入口、主要流程、資料流、狀態、UI 更新與外部依賴
- 區分目前仍在運作的程式碼、可能已廢棄的程式碼，以及無法確認的部分
- 最後整理成一份可以供未來重構或重新實作使用的功能規格

請以「現有程式碼證據」為主要依據，不要因為某種設計看起來合理，就假設原系統一定如此。

# AI 分析要求

請依下列順序分析。

## A. 找入口

確認：

- 哪些 UI event、route、function 或 class 會進入此功能
- 我提供的入口是否真的是主要入口
- 是否還有其他入口

---

## B. 向下追蹤 Call Flow

從入口開始追蹤主要執行流程，例如：

```text
button click
→ handler
→ showCommentary()
→ loadCommentary()
→ API
→ transform
→ render
```

不要只列 function 名稱。

請簡短說明每一步「做什麼」。

---

## C. 向上追蹤 Caller

對重要 function，也要找：

> 誰呼叫它？

尤其確認：

- 使用者操作是否會觸發
- 經文切換是否會觸發
- 初始化是否會觸發
- 是否有其他功能間接呼叫

---

## D. Data Flow

請追蹤主要資料如何流動。

例如：

```text
book / chapter / verse
→ request parameter
→ API response
→ internal data structure
→ rendered HTML
```

特別注意：

- function parameter
- return value
- global variable
- module state
- class property
- localStorage / IndexedDB
- cache
- event payload

---

列出此功能會讀取或修改的重要 state。

- cache
- DOM

- browser storage

並指出有哪些 side effects。

- 資料轉換

- event binding

## G. 外部依賴

## H. 找可能的 Dead Code

對看似相關的程式碼，不要因為名稱相似就認定正在使用。

請標示：

- 明確在 runtime path 中
- 可能仍使用

- 無法確認

如果沒有足夠證據，請不要建議刪除。

# 證據可信度

分析結果請嚴格區分三種：

## Confirmed

有明確程式碼證據。

例如：

> `changeVerse()` 明確呼叫 `reloadCommentary()`。

## Inferred

根據程式結構合理推論，但目前沒有完整證據。

例如：

> `commentaryCache` 看起來是避免重複 API request 使用，但尚未找到所有讀寫位置。

## Unknown

目前程式碼不足以確認。

例如：

> 尚無法確定 cache 是否跨 chapter 共用。

**不要把 Inferred 寫成 Confirmed。**

只記錄從程式碼觀察到的重要行為。

例如：

不要把所有搜尋到的檔案全部列進來。

分成：

- 高度可能已未使用
- 可疑
- 無法確認

並附上判斷理由。

## 9. Confirmed / Inferred / Unknown

## 10. Recovered Feature Specification

最後請把目前觀察到的實際行為，整理成一份不依賴實作細節的功能規格。

例如：

```text

- 顯示對應經節的注解內容
```

# 重要限制

- 這次不要重構程式碼
- 不要大量提出新架構
- 不要因為舊程式不好看就判定它是錯的
- 不要把未被呼叫的 function 自動視為 dead code
- 不要只靠檔名或 function 名稱判斷用途
- 優先追實際 caller / callee / import / event / runtime path
- 發現範圍外的重要問題，可以記錄，但不要無限制擴大調查
- 如果我的記憶與程式碼衝突，請明確指出
- 如果沒有證據，直接寫「目前無法確認」，不要補一個合理答案
