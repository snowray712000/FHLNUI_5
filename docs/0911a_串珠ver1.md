# 功能逆向分析

我要你針對既有專案中的一個功能，進行 **feature-by-feature reverse engineering（逐功能逆向分析）**。

目標不是重構程式碼，也不是提出新的架構，而是：

- 從現有程式碼反推出這個功能實際如何運作
- 找出它的入口、主要流程、資料流、狀態、UI 更新與外部依賴
- 區分目前仍在運作的程式碼、可能已廢棄的程式碼，以及無法確認的部分
- 最後整理成一份可以供未來重構或重新實作使用的功能規格

請以「現有程式碼證據」為主要依據，不要因為某種設計看起來合理，就假設原系統一定如此。

# 2. 我認為這個功能的目的

我目前理解這個功能主要是：

[請填寫]
- 它是一本書，電子化後，被處理成 api。
  - api 介紹，裡面的 sc.php
    - https://bible.fhl.net/json/ 
  - 例如
    - https://bible.fhl.net/json/sc.php?book=4&engs=Gen&chap=1&sec=1&gb=0
      - 注意，book = 4，是 串珠註釋書。而程式內 book 字眼，可能指的是「第幾卷」書，例如 1 是創世記。
      - 注意，book = 3，其實就是 註釋 資料，也就是它們共用一個 api。
- 每一節，都有對應到不同的內容
- 內容 可能包含，「分段」
  - 例如 創1:1 的回傳結果 `\n  1;  God creates heaven and earth;\n  3;  the light;\n  6;  the firmament;\n  9;  separates the dry land;\n 14;  forms the sun, moon, and stars;\n 20;  fishes and fowls;\n 24;  cattle, wild beasts, and creeping things;\n 26;  creates man in his own image, blesses him;\n 29;  grants the fruits of the earth for food.\n\n * beginning.\n # Pr 8:22-24; 16:4; Mr 13:19; Joh 1:1-3; Heb 1:10; 1Jo 1:1|\n * God.\n # Ex 20:11; 31:18; 1Ch 16:26; Ne 9:6; Job 26:13; 38:4; Ps 8:3; 33:6,9|\n # Ps 89:11,12; 96:5; 102:25; 104:24,30; 115:15; 121:2; 124:8; 134:3|\n # Ps 136:5; 146:6; 148:4,5; Pr 3:19; 8:22-30; Ec 12:1; Isa 37:16; 40:26|\n # Isa 40:28; 42:5; 44:24; 45:18; 51:13,16; 65:17; Jer 10:12; 32:17|\n # Jer 51:15; Zec 12:1; Mt 11:25; Ac 4:24; 14:15; 17:24; Ro 1:19,20|\n # Ro 11:36; 1Co 8:6; Eph 3:9; Col 1:16,17; Heb 1:2; 3:4; 11:3; 2Pe 3:5|\n # Re 3:14; 4:11; 10:6; 14:7; 21:6; 22:13|\n\n`

  - 關鍵字，可能是一個單字，也可能是一個子句。
  - 也可能是對這個字的註釋
- 內容，可能 包含 相節相關的描述

# AI 分析要求

請依下列順序分析。

## A. 找入口

確認：

- 哪些 UI event、route、function 或 class 會進入此功能
- 我提供的入口是否真的是主要入口
- 是否還有其他入口

---

## B. 向下追蹤 Call Flow

從入口開始追蹤主要執行流程，例如：

```text
button click
→ handler
→ showCommentary()
→ loadCommentary()
→ API
→ transform
→ render
```

不要只列 function 名稱。

請簡短說明每一步「做什麼」。

---

## C. 向上追蹤 Caller

對重要 function，也要找：

> 誰呼叫它？

尤其確認：

- 使用者操作是否會觸發
- 經文切換是否會觸發
- 初始化是否會觸發
- 是否有其他功能間接呼叫

---

## D. Data Flow

請追蹤主要資料如何流動。

例如：

```text
book / chapter / verse
→ request parameter
→ API response
→ internal data structure
→ rendered HTML
```

特別注意：

- function parameter
- return value
- global variable
- module state
- class property
- localStorage / IndexedDB
- cache
- event payload

---

列出此功能會讀取或修改的重要 state。

- current verse
- selected commentary
- cache
- DOM
- global object

- browser storage

並指出有哪些 side effects。

## F. UI 更新

找出真正把結果顯示到 UI 的位置。

請區分：

- 資料取得
- 資料轉換
- HTML / DOM 產生
- UI render
- event binding

## G. 外部依賴

列出功能依賴：

## H. 找可能的 Dead Code

對看似相關的程式碼，不要因為名稱相似就認定正在使用。

# 證據可信度

分析結果請嚴格區分三種：

## Confirmed

有明確程式碼證據。

例如：

> `changeVerse()` 明確呼叫 `reloadCommentary()`。

## Inferred

根據程式結構合理推論，但目前沒有完整證據。

例如：

> `commentaryCache` 看起來是避免重複 API request 使用，但尚未找到所有讀寫位置。

## Unknown

目前程式碼不足以確認。

例如：

> 尚無法確定 cache 是否跨 chapter 共用。

**不要把 Inferred 寫成 Confirmed。**
