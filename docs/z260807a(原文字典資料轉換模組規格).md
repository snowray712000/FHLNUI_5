# 原文字典資料轉換模組規格（供另一專案 TDD 參考）

> 本文件聚焦於「原文字典」這個功能**最核心的資料層**：從 API 取得字典原始 JSON、轉換成 `DText[]`、再轉成 HTML 的完整管線（`SnDictOfTwcb`／`SnDictOfCbol`／`twcbflow`／`cbolflow` 及其共用的字串切割工具）。
>
> 這一層是**純資料轉換邏輯**（除了 `queryAsync` 內的 ajax 呼叫外，`cvtToDTexts` 全部是同步、無副作用的字串處理），因此最適合寫成 TDD 的單元測試對象。
>
> 「點擊 `.sn` 之後怎麼觸發彈窗、`DialogHtml` 容器機制、事件委派三條路徑」這一層**不是**本文件重點，完整規格見 [z260806b(SN即時字典彈窗功能規格).md](z260806b(SN即時字典彈窗功能規格).md)；「同源字（`same[]`）清單」子功能見 [z260806a(同源字功能規格).md](z260806a(同源字功能規格).md)。本文件與該兩份文件有少量重疊（例如 `queryDictionaryAndShowAtDialogAsync` 的角色），但切入角度不同：那兩份文件從「使用者點擊 → 開哪個彈窗」的角度寫，本文件從「字典 API 回傳的字串 → 怎麼被剖析成 DText[] → 怎麼被渲染」的角度寫。
>
> 撰寫時間：2026-08-07。

## 1. 整體資料流

```
原文字典 API (sd.php / sbdag.php / stwcbhdic.php)
  → { record: [{ dic_text, edic_text?, sn, ... }] }   (原始 JSON)
  → ISnDictionary 實作類別（SnDictOfTwcb / SnDictOfCbol）
      .queryAsync(param)   把 API 包成 Promise，回傳原始 JSON
      .cvtToDTexts(data)   把 dic_text/edic_text 字串轉成 DText[]
          ↳ twcbflow(str)  或  cbolflow(str)
              ↳ splitBtw()       先切出巢狀容器（<div class="idt">…</div>、<span class="exp">…</span> 等）
              ↳ splitBrOne()     再切換行符號 \r\n → { isBr: 1 }
              ↳ splitReference() 最後切出交互參照 #創1:1| → { w, refAddresses }
  → cvtDTextsToHtml(dtexts)   DText[] → HTML 字串
  → 塞進 DialogHtml 或 ParsingPopUp 等容器顯示
```

三個字串切割工具（`splitBtw`／`splitBrOne`／`splitReference`）是**與字典無關的通用工具**，`twcbflow`／`cbolflow` 只是用不同順序、不同正規表達式組合它們。這代表另一專案重新實作時，可以先把這三個工具當「最底層、最容易寫單元測試」的積木來 TDD，字典 flow 函式本身只是組裝邏輯。

## 2. API 總覽

| API | 用途 | 對應的資料來源方 | 呼叫類別 |
|---|---|---|---|
| `GET /json/sd.php?N={0\|1}&k={sn}&gb=0` | CBOL 字典（中文 `dic_text` + 英文 `edic_text`） | CBOL 計畫 | `SnDictOfCbol` |
| `GET /json/sbdag.php?k={sn}&gb=0` | 浸宣字典·新約部分 | 浸宣出版社（twcb） | `SnDictOfTwcb`（`isOld=false` 時） |
| `GET /json/stwcbhdic.php?k={sn}&gb=0` | 浸宣字典·舊約部分 | 浸宣出版社（twcb） | `SnDictOfTwcb`（`isOld=true` 時） |

- `N`：0=新約(Greek)，1=舊約(Hebrew)。`sd.php` 才有這個參數；`sbdag.php`/`stwcbhdic.php` 是靠選對 API（新約用 sbdag，舊約用 stwcbhdic）來區分，不靠參數。
- `gb`：0=繁體，1=簡體。目前程式碼固定傳 `0`。
- 回傳格式：`{"status":"success","record_count":1,"record":[{"sn":"00113","dic_text":"...","edic_text":"...(僅sd.php有)","dic_type":1,"orig":"אָדוֹן"}]}`。
- `dic_text`／`edic_text` 內文可能包含 HTML 片段（`<div class="idt">`、`<span class="exp">`、`<span class="bibtext">`）與 `\r\n` 換行，也可能包含交互參照語法 `#創1:2;出2:3-4|`。**這就是 twcbflow/cbolflow 要處理的輸入格式。**
- CORS：正式站直接打 `/json/xxx.php`（同網域）；本地開發（`isRDLocation()` 判斷 `file://`／`127.0.0.1`／`localhost`）需要走 `http://127.0.0.1:5600` 的本機 proxy（Python flask 寫的），proxy 沒開則 fallback 讀本機假資料檔（`index/sd_virtual_new.json`、`sd_virtual_old.json`、`sd_virtual_new_twcb.json`、`sd_virtual_old_twcb.json`）。

## 3. `ISnDictionary` 介面與兩個實作

檔案：`index/ISnDictionary.es2023.js`

```js
export class ISnDictionary {
    /** @param {{sn:string, isOld:boolean}} param
     *  @returns {Promise<DataOfDictOfFhl>} 抽象方法 */
    async queryAsync(param) { throw new Error("...") }

    /** @param {DataOfDictOfFhl} dataOfFhl
     *  @returns {DText[]} 抽象方法 */
    cvtToDTexts(dataOfFhl) { throw new Error("...") }
}
```

這是一個很單純的兩方法介面：`queryAsync` 負責「拿資料」（含網路 I/O），`cvtToDTexts` 負責「轉格式」（純函式）。兩個子類別各自對應一個資料來源：

### 3.1 `SnDictOfTwcb`（浸宣字典）

檔案：`index/SnDictOfTwcb.es2023.js`

```js
export class SnDictOfTwcb extends ISnDictionary {
    queryAsync(param) {
        // param: {sn:string, isOld:boolean}
        let url = param.isOld ? "/json/stwcbhdic.php" : "/json/sbdag.php"
        url += "?k=" + param.sn + "&gb=0"
        // isRDLocation()==false: 直接打 url，回傳字串要手動 JSON.parse
        // isRDLocation()==true : 先打 http://127.0.0.1:5600${url}（proxy），失敗則讀本機假資料 json 檔
    }
    cvtToDTexts(dataOfFhl) {
        return twcbflow(dataOfFhl.record[0].dic_text)  // 只處理中文，沒有 edic_text
    }
}
```

要點：
- `queryAsync` 回傳的 Promise resolve 值，正式站是**字串**（`res(JSON.parse(reStr))`——注意這裡已經 parse 過了，所以最終還是物件）；本地開發走假資料時是 jQuery `$.ajax` 對 `.json` 檔案自動解析出的物件，程式碼又多包一層 `JSON.stringify` 再 `JSON.parse`，是為了讓兩條路徑最終格式一致（見程式碼註解 `virtualNewOld`）。
- `cvtToDTexts` 只吃 `dic_text`，浸宣字典沒有對應的英文欄位。
- 檔案內留有大段被註解掉的 ES6 舊版本實作（`function SnDictOfTwcbEs6Js()`），邏輯與現行 class 完全相同，只是包裝風格不同——這是專案「保留舊版本程式碼在同檔案底部當註解」的慣例，另一專案不需要照抄這個習慣，純作參考。

### 3.2 `SnDictOfCbol`（CBOL 字典）

檔案：`index/SnDictOfCbol.es2023.js`

```js
export class SnDictOfCbol extends ISnDictionary {
    queryAsync(param) {
        let val = "?N=" + (param.isOld ? "1" : "0") + "&k=" + param.sn + "&gb=0"
        let url = "/json/sd.php" + val
        // isRDLocation()==false: 打 url，注意：sd.php 回傳的字串已經是合法 JSON 物件格式的字串，
        //                        但呼叫端故意不再 JSON.parse（"res(reStr) // sd.php 回傳本來就是一個 json 物件，所以不要再用 JSON.parse"）
        //                        —— 這裡有個潛在技術債陷阱，見 [z260806a] 第2節對 sd.php 回傳格式的完整說明
        // isRDLocation()==true : proxy 或本機假資料 sd_virtual_new.json / sd_virtual_old.json
    }
    cvtToDTexts(dataOfFhl) {
        let ch = cbolflow(dataOfFhl.record[0].dic_text)   // 中文
        let en = cbolflow(dataOfFhl.record[0].edic_text)  // 英文
        return Enumerable.from(ch).concat([{ isBr: 1 }, { isHr: 1 }]).concat(en).toArray()
        // 中文結果 + 換行 + <hr/> 分隔線 + 英文結果，接成同一個 DText[]
    }
}
```

要點：
- CBOL 字典有中英文兩份（`dic_text`／`edic_text`），各自跑一次 `cbolflow`，中間插入 `{isBr:1},{isHr:1}` 分隔。
- 這裡用了 `Enumerable`（linq.js 全域變數，專案慣例透過 `<script>` 全域載入，不是 import），另一專案若不用 linq.js，直接用陣列 `.concat()` 即可達到相同效果。
- **注意 `queryAsync` 回傳值型別的不一致**：`SnDictOfTwcb.queryAsync` 回傳的是已 parse 過的物件；`SnDictOfCbol.queryAsync`（正式站分支）回傳的是**字串**（未 parse，註解特別強調「不要再 parse」）。呼叫端 `queryDictionaryAndShowAtDialogAsync` 若要統一處理兩者，需留意這個型別落差是否已經妥善銜接（目前呼叫端把兩者都當物件用 `.record[0]` 存取，若 `SnDictOfCbol` 正式站真的回傳字串，理論上會出錯——這是原始碼裡的一個可疑點，另一專案重新設計 interface 時建議讓 `queryAsync` 明確保證回傳「已 parse 的物件」，兩個實作都要一致）。

## 4. 資料轉換管線細節

### 4.1 `twcbflow(str)`（浸宣字典專用）

檔案：`index/twcbflow.es2023.js`

處理步驟（依序）：

1. **`splitBtw(str, {reg1: /<div class="idt">/g, reg2: /<\/div>/g})`**：把巢狀的 `<div class="idt">...</div>` 切成 `{tpContainer: '<div class="idt">', children: DText[]}` 結構（巢狀 div 會遞迴產生巢狀 `children`）。若原字串完全沒有 `<div class="idt">`，`splitBtw` 回傳 `null`，此時 fallback 成 `[{w: str}]`。
2. **`splitSpansOne`**（`twcbflow` 內的區域函式）：對每個節點（若沒有 `tpContainer` 代表是純文字節點）再用 `splitBtw` 切一次 `<span class="bibtext">`／`<span class="exp">`（`reg2: /<\/span>/g`），若有 `tpContainer`（代表是上一步切出來的 div），則遞迴處理它的 `children`。
3. **`splitBrOne`**：把所有節點內的 `\r\n` 換行切成 `{isBr: 1}` 標記節點。
4. **`splitReference`**：把 `#創1:1;出2:3-4|` 這種交互參照語法切成 `{w, refAddresses: [{book,chap,verse},...]}`。

`splitBtw` 的演算法本質：先用兩個正規表達式各自找出所有「開始標記」與「結束標記」的位置（`{i, cnt, tp:0|1}`），依位置排序後，用類似括號配對演算法（`cnt` 計數器）找出每一組開始/結束的配對（`findPair`，支援巢狀），最後依配對位置把原字串切成 `{w:純文字}` 與 `{tpContainer, w, w2, children}`（容器節點）交錯的陣列。這個演算法**與具體標籤無關**，傳入不同的 `reg1`/`reg2` 就能切任何「有開始/結束標記」的巢狀結構，不限於 HTML。

### 4.2 `cbolflow(str, isEng)`（CBOL 字典專用）

檔案：`index/cbolflow.es2023.js`

處理步驟：

1. **`splitBrOne(str)`**：先切換行（注意順序與 `twcbflow` 相反：CBOL 沒有 HTML 容器要先切，直接從切換行開始）。
2. **`findIdxOr3NewLineNewLine`**：找出「連續出現 3 組『兩個相鄰換行』」的位置索引。CBOL 字典本文的結構通常是：
   ```
   0128 'Adamah {a-da:-ma:'}      ← 字彙標題
   （換行換行）
   與 0127 同; 專有名詞 地名        ← 詞源
   （換行換行）
   欽定本 - Adamah 1; 1            ← 使用統計（含「1」這種會誤判成經文的數字）
   （換行換行）
   亞大瑪 = "地土"                  ← 字義起點，從這裡才需要偵測交互參照
   1) 拿弗他利的城鎮 (#書 19:36|)
   ```
   前三段（標題/詞源/統計）刻意不跑 `splitReference`，因為「欽定本 - Adamah **1**; 1」這種孤立數字容易被誤判成經文章節。只有從第 3 個「換行換行」之後的內容才切交互參照。
3. 若找不到 3 組換行換行（`idx == -1`，代表本文很短，例如只是一段解釋文字），則整段直接跑 `splitReference`；否則前半段原樣保留、後半段才切 `splitReference`（`splitWhen3NewLineExist`）。

### 4.3 `splitReference`（交互參照剖析，`twcbflow`/`cbolflow` 共用）

檔案：`index/splitReference.es2023.js`。這是整個模組中最複雜的部分，獨立成一個純函式，輸入可以是 `string` 或 `DText[]`（陣列輸入時會遞迴處理每個節點的 `.w`，遇到 `tpContainer` 節點則遞迴處理 `.children`）。

核心流程（`splitWhenStringInput`）：

1. `findRefernece(str)`：
   - 先把所有已知書卷名稱（中文全名/簡稱/簡體、英文全名/縮寫，來自 `BibleConstant`）依長度**由長到短**排序組成一個大 regex 的 or 群組（避免「羅」被「羅馬」的前綴誤判截斷）。
   - `splitByBook`：先用書卷名把字串切段，確保像 `1Ti`（提摩太前書英文縮寫）這種「數字+書卷名」不會讓數字被前一段誤吃。
   - 對每一段跑主 regex：`(#)?(書卷名)?(?: |&nbsp;)?( 六種經文範圍格式之一 )(;)?(\|)?`，六種格式對應 `tp: 'a'~'f'`：
     | tp | 格式範例 | 意義 |
     |---|---|---|
     | a | `31:12-32:12` | 跨章範圍 |
     | b | `31:12-e`/`31:12-end` | 到章末 |
     | c | `31:12-15,18,19-31` | 同章內範圍+列舉 |
     | d | `31:12,15,17` | 同章內列舉 |
     | e | `4-12` | 承接上一個章節的節範圍（沒有寫章號） |
     | f | `12`（單一數字，前面無 `:`） | 最模糊的情況——可能是章號、可能只是普通數字 |
   - 沒有匹配到書卷名時，`book` 沿用「上一個有寫的 book」或呼叫端傳入的 `addrDefault.book`。
2. `merge`：把連續、中間沒有被純文字打斷的多個 `DRef` 合併成一個 `DRefs{refs:[]}` 容器（因為 `#創1:1;2:3|` 這種要當成同一組交互參照整體處理）。
3. `removeTpf`：**修正 tp='f' 的誤判**——如果某個 `tp:'f'`（純數字、無書卷名）沒有被 `#`/`|` 包住（`isS`/`isE` 皆無），代表它很可能只是句子裡的普通數字（例如「殘忍 **2** #約12:21|」的 `2`），會被還原成純文字 `{w: ...}` 並與前後文字合併。
4. `connectPureStringCauseOfTypeFRemove`：上一步移除後，相鄰的純文字節點合併回一個（避免文字被切得太碎）。
5. `cvtToDTexts`：把 merge 完的 `DRefs.refs[]` 依 `tp` 分別呼叫 `BibleConstantHelper.generateAddressesTpA/TpB/TpE/TpF(...)` 展開成完整的 `{book,chap,verse}[]` 位址陣列，掛在該節點的 `.refAddresses` 上，`.w` 則是原始顯示文字（例如 `#創1:1,5,7-9;2:3-1|`）。

輸出範例（來自 `ijnjs/cbolflow.spec.js` 的既有測試資料）：
```js
[
  { w: "1) 拿弗他利的城鎮 (" },
  { w: "#書 19:36|", refAddresses: [{ book: 6, chap: 19, verse: 36 }] },
  { w: ")" }
]
```

## 5. 產出的 DText[] 範例（完整結構）

以 `ijnjs/twcbflow.spec.js` 的測試資料為準（舊約字典 `00011` 條目，`<div class="idt">`巢狀 + `<span class="bibtext">`/`<span class="exp">`巢狀 + 交互參照）：

```js
twcbflow(dic_text)
// re[21] ≈ {
//   tpContainer: '<div class="idt">',
//   w: '<div class="idt">', w2: '</div>',
//   children: [
//     { w: "一、指陰間裡停放要滅亡的死人之處，是陰間有分隔間的概念發展之後產生的字。" },
//     {
//       tpContainer: '<span class="bibtext">',
//       children: [
//         { tpContainer: '<span class="exp">', children: [{ w: "燬滅" }] }
//       ]
//     },
//     { w: "，平行字שְׁאוֹל陰間，" },
//     ...
//     { w: "#伯26:6;箴15:11|", refAddresses: [
//         { book: 18, chap: 26, verse: 6 },
//         { book: 20, chap: 15, verse: 11 }
//     ]},
//     ...
//   ]
// }
// re[22] = { isBr: 1 }
```

這個帶巢狀 `tpContainer`/`children` 的結構，最終交給 `index/cvtDTextsToHtml.es2023.js` 轉回 HTML（渲染規則不在本文件範圍，但可從 `tpContainer` 字串本身反推要輸出的標籤/class）。

## 6. 呼叫端整合範例：`queryDictionaryAndShowAtDialogAsync`

檔案：`index/queryDictionaryAndShowAtDialogAsync.es2023.js`

這是唯一把 `SnDictOfTwcb` 與 `SnDictOfCbol` 兩個資料源**同時**用上的生產程式碼（其餘細節、彈窗容器機制見 [z260806b] 第5節，這裡只重述資料流部分）：

```js
function qDataOfDictOfFhlAsync(param) {
    let iQueryor = [new SnDictOfTwcb(), new SnDictOfCbol()]
    return iQueryor.map(a1 => a1.queryAsync(param))
        .map((promise, i) => promise.then(data => {
            data.src = i == 0 ? "twcb" : "cbol"   // 用陣列 index 記來源，事後用來決定要呼叫哪個 cvtToDTexts
            data.isOld = param.isOld
            return data
        }))
}
// 平行 queryAsync → 各自 cvtToDTexts → 各自 cvtDTextsToHtml → 拼字串：
// htmlTwcb + "<br/>" + 浸宣授權聲明 + "<br/>" + htmlCbol + "<br/>" + CBOL授權聲明
```

授權聲明是寫死的 HTML 字串：
```html
<span class="bibtext">以上資料由<a href="http://twcb.fhl.net/" target="_blank">浸宣出版社</a>授權</span>
<span class="bibtext">以上資料由<a href="https://bible.fhl.net/part1/cobs1.html" target="_blank">CBOL計畫</a>整理</span>
```
另一專案重新實作時，若要保留同樣的資料授權聲明，需注意這兩段文字是**業務需求**（授權條款要求），不是隨意的裝飾文字。

## 7. 舊專案角色 / 新舊對照

### 7.1 `ijnjs/` 底下的 ES6 前身

- `ijnjs/SnDictOfTwcb.es6.js`、`ijnjs/twcbflow.es6.js`、`ijnjs/cbolflow.es6.js`：目前的 `index/*.es2023.js` 版本邏輯上幾乎是逐行照搬（`class extends ISnDictionary` 換成 `XxxEs6Js()` 函式包裝 + `Xxx.prototype = new ISnDictionary()`），差別只在模組系統（`import`/`export` vs 全域函式）。**這組是 twcbflow/cbolflow 目前唯一有測試覆蓋的版本**（見第8節）。
- 現行 `index/*.es2023.js` 檔案內大量保留被註解掉的 ES6 風格程式碼（同檔案下半部），是本專案「重構時原地保留舊版本當註解，暫不刪除」的過渡期慣例。

### 7.2 更早期：`index/DialogTemplate/` 底下的字串拼接式實作

這一組是比 ES6 版本**更早一代**的實作，走「同步 ajax + 純字串正規表達式替換」路線，完全不經過 `DText[]` 中介格式：

- **`index/DialogTemplate/OrigDict.js`**：`OrigDict.prototype.queryFromApi(sn, isOld, isGb)` 用**同步**的 `$.ajax({async:false})` 依序打 `sd.php`（CBOL）與 `sbdag.php`/`stwcbhdic.php`（twcb），直接回傳一個扁平陣列 `[{w, isOld, sn, orig, ver}]`（`ver` 是版本標籤如 `'CBOL Parsing 系統'`/`'浸宣出版社'`），**沒有 DText 巢狀結構、沒有交互參照解析**，`dic_text` 就是原始字串直接塞進 `.w`。
  - 本機開發（`_isLocalHost()` 判斷同 `isRDLocation()`）時，`_queryFromTwcbApi` 會呼叫 `OrigDictPresudo`（同檔案內，一組回傳寫死 JSON 字串的假資料函式：`presudo_New113a/b`、`presudo_Old113a/b`），這組假資料在 `tests/sn-dictionary-dialog2.js` 裡也被複製貼上了一份一模一樣的（`OrigDict`/`OrigDictPresudo` 重複定義），可見這是專案裡「查詢 SN=113 的字典假資料」的標準測試素材，橫跨多個檔案沿用。
- **`index/DialogTemplate/ParsingOrigDict.js`**：提供三個字串處理函式，是 `twcbflow`/`splitReference` 的**前身雛型**：
  - `addBreakLine(data)`：用 `Ijnjs.SplitStringByRegex` 依 `\r?\n` 切出 `{br:1}` 節點——對應現行的 `splitBrOne`。
  - `addOrigDict(data)`：用正規表達式 `/(G|H)(\d+[a-z]?)/gi` 切出「文字中提到的其他 SN 編號」（例如字典解釋裡出現的「見 κόλπος G2859」），標記 `sn`/`isOld`——這是**現行版本沒有對應功能**的地方，`twcbflow.es2023.js`/`cbolflow.es2023.js` 目前不會把字典本文內文提到的其他 SN 轉成可點擊連結，只有交互參照（經文）與最外層本身的 SN 才會連結化。另一專案若想還原這個「字典內文互相連結」的功能，可以參考這支舊程式碼的正規表達式。
  - `addReference(data, book, chap)`：更早期版本的交互參照切法，書卷名比對邏輯（`getAllBookNamesAndOrderByLengthDesc`）、正規表達式組合方式（`getRegExpForReference2`）與現行 `splitReference.es2023.js` 的 `findRefernece` 神似（長度排序避免前綴誤判、書卷名可省略），可視為同一邏輯的**兩次獨立重寫**（新版多了 a~f 六種格式分類、`removeTpf` 誤判修正等現行版本才有的細節）。
- **`index/DialogTemplate/SnDictDialog.html`**：Bootstrap 4 `.modal` 版型（非 jQuery UI dialog），字典彈窗的**更早期 UI 容器**，現行生產流程已改用 `DialogHtml`（jQuery UI 封裝，見 [z260806b] 第3節），不再使用 Bootstrap modal。
- 這一整組檔案（`OrigDict`/`ParsingOrigDict`/`SnDictDialog.html`/`DialogTemplate.js`）目前**只在「非最新版本」相容模式下才會被動態載入**（`index/index.js:154-160`，條件 `AppVersion.s.testIsLastVersion() == false`，同一批載入的還有 `../static/js/` 底下的舊版 Vue 打包檔），代表這是給「還沒更新到最新版本的使用者」保留的舊版相容路徑，**不是目前主要使用者會走到的程式碼**。

### 7.3 另一條至今仍存活、但獨立於 DText[] 管線之外的實作：`ParsingPopUp`

檔案：`index/ParsingPopUp.es2023.js`——這是**目前仍在運作**，但採用**與本文件主流程完全不同技術路線**的第三套字典彈窗實作：

- 用途：`.snParse` 元素（原文 Parsing 分析結果裡，點擊某個詞形跳出的小 popup，與本文件第1~6節「點 `.sn` 開字典彈窗」是不同的觸發點）。
- 資料源：同樣打 `sd.php`（`getAjaxUrl('sd', ps)`）+ `sbdag.php`/`stwcbhdic.php`（`getAjaxUrl('sbdag'|'stwcbhdic', ps)`），但**完全不經過 `SnDictOfTwcb`/`SnDictOfCbol`/`twcbflow`/`cbolflow`/DText[]**，而是拿到 `dic_text` 字串後直接用一系列 `String.replace(regex, ...)` 就地產生 HTML 字串（`parseDic`、`parse_dic_stwcbhdic` 兩個區域函式）：
  - `parseDic(text)`：把「於」「自」「參」「見」「from」「and」等關鍵字後面接的數字包成 `<span class='snParse sn'>`；`#...|` 包成 `<span class='searchBibleVerse'>`；空白轉 `&nbsp;`；`\r\n` 轉 `</br>`。
  - `parse_dic_stwcbhdic(html)`：`\r\n` 轉 `<br />`；用 `parseRef`（內部產生的 regex 與 `splitReference` 的書卷名比對邏輯概念相同，但實作是直接 `.replace()` 包 `<span class='ref'>` 而非產生結構化 `DText[]`）處理交互參照；用 unicode range regex（`[֐-׾]`希伯來文／`[Ͱ-Ͽἀ-῿]`希臘文）把原文字元包成 `<span class='hebrew-char'>`/`<span class='greek-char'>` 放大顯示。
- 本地開發假資料：`index/dev_sbdag.es2023.js`、`index/dev_stwcbhdic.es2023.js`——各自 hardcode 一筆真實字典資料（`dic_text` 用 unicode escape 寫死），`isLocalHost()` 為真時直接回傳這個，取代真正的 ajax 請求。寫法與 `SnDictOfTwcb`/`SnDictOfCbol` 的「本機 proxy → 讀虛擬 json 檔」策略不同（這裡是直接把假資料寫死在 `.js` 檔的函式回傳值裡，不需要額外的 `.json` 檔）。
- **給另一專案的啟示**：同一個「字典本文轉 HTML」的需求，本專案裡實際存在（至少）三套互相獨立、邏輯不完全一致的實作（`SnDictOfTwcb+twcbflow` 結構化路線／`ParsingOrigDict` 舊結構化路線／`ParsingPopUp` 直接字串替換路線）。若要重新設計，建議**只採用本文件第3~6節「DText[] 中介格式」這一條路線**（結構清楚、可測試、渲染邏輯可與資料邏輯分離），`ParsingPopUp` 那種直接對 HTML 字串 `.replace()` 的作法容易因為 regex 順序、跳脫字元問題產生難以定位的 bug，不建議沿用。

## 9. 給另一專案 TDD 實作的建議順序

1. **先做三個通用字串工具**（互相獨立，可平行開發）：
   - `splitBtw(str, {reg1, reg2})`：巢狀開始/結束標記配對切割。測試重點：無巢狀單層配對、多層巢狀、多組同層配對、找不到配對回傳 `null`。
   - `splitBrOne(strOrDTexts)`：`\r\n`／`\n` 換行切割成 `{isBr:1}`。測試重點：純字串輸入、`DText[]` 輸入（含 `tpContainer` 節點要遞迴處理 `children`）、字串陣列。
   - `splitReference(strOrDTexts, addrDefault)`：交互參照剖析。測試重點：對照第4.3節表格，六種 `tp` 格式各寫至少一個案例；`removeTpf` 誤判修正案例（純數字不誤判成經文）；書卷名前綴誤判案例（如「羅」不應截斷「羅馬書」全名比對，或反向：先出現長名稱不應被短名稱搶先命中）。
2. **再做 `twcbflow`/`cbolflow`**：用上面三個工具組裝，測試可以直接沿用 `ijnjs/twcbflow.spec.js`／`ijnjs/cbolflow.spec.js` 既有的測試資料與期望輸出（第8節），但改寫成新專案的測試框架語法。
3. **`ISnDictionary` 兩個實作**：`cvtToDTexts` 部分幾乎不需要額外測試（已被 twcbflow/cbolflow 涵蓋），重點是 `queryAsync` 的 **URL 組裝邏輯**（`sn`/`isOld`/`gb` 參數位置）要能脫離真實網路獨立測試——建議設計成可注入 fetch/ajax 實作（依賴反轉），而不是像現行版本一樣把 `$.ajax` 寫死在函式內部，這樣才能對「URL 組對了沒」寫單元測試，不需要真的發網路請求或 mock 全域 `$`。
4. **`queryDictionaryAndShowAtDialogAsync` 整合層**：測試重點是「兩個資料源平行查詢、各自轉換、合併輸出」的邏輯（第6節），可以用假的 `ISnDictionary` 實作（回傳固定 `DText[]`）來測試合併/組字串部分，不需要真的呼叫 `twcbflow`/`cbolflow`。
