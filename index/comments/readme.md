# parseComment 設計說明（摘要／前言／動機／目的／方法）

## 摘要
`parseComment` 的設計目標是把「Legacy 註釋純文字」轉換成可被後續流程穩定使用的**結構化資料（Tree/Blocks/Tokens）**，並刻意將「資料結構化（Parsing）」與「視覺呈現（Rendering）」解耦。整體流程以 **前處理 → 逐行詞法分析 → 區塊偵測（含表格）→ 建樹 → 正規化** 為主，對應的關鍵模組包含 `preprocessCaseToLines`、`tokenizeLine`、`detectTableBlocks`、`buildTree`、`normalizeTree` 等。

---

## 前言（情境）
註釋資料來源通常是長年累積的純文字內容，具有以下特性：

- 文字內容以「縮排、空白、換行」承載層級與段落意義，但格式不一致。
- 同時混雜多種段落型態：一般段落、清單（有序/無序）、引言、註解、以及偶發的表格。
- 不同書卷、不同作者、甚至同一份資料內部，規則也可能漂移。

在此情境下，若直接以 UI 需求（例如 HTML 排版）為導向去解析，容易使邏輯分散、難以測試與維護。因此 `parseComment` 以「先把資料解析成穩定中介結構」為核心。

---

## 動機（問題）
純文字註釋的主要工程問題可抽象成：

1. **空白的語意不單一**  
   同樣是空白與縮排，可能代表：  
   - 層級（child/sibling 的結構）  
   - 換行排版（內容其實要接回上一行）  
   - 對齊（例如表格、或固定欄寬的排版）

2. **符號/特徵字決定段落型態，但分布複雜**  
   常見如 `● ◎ ○ ☆`、`壹、 一、 （一） 1. A. (1) a.` 等，但也存在「看似清單卻無符號」的段落（例如 `時間：... 地點：...` 連續多行）。

3. **表格是非連續、非完美對齊的特殊區塊**  
   需要先辨識「這一段是表格」，再用不同規則處理，否則會被一般縮排/斷行規則破壞。

4. **需要可測試、可演進**  
   因為規則會隨案例擴充而調整，流程必須能被拆成小函式並以單元測試鎖定行為（對應 `tests/註釋排版/*_test.js` 的分段測試）。

---

## 目的（具體目標）
`parseComment` 的具體目標可描述為：

- **輸入**：一段註釋 raw text（或「case」格式文字）。
- **輸出**：一致的結構化結果（例如節點樹、段落區塊、token 序列），讓後續：
  - UI 渲染只需消費結構，不需理解雜訊格式。
  - 搜尋、索引、引用、段落折疊等功能能依結構運作。
- **約束**：
  - 規則要能容忍縮排不固定（偏向相對縮排，而非固定 4 格）。
  - 對表格等特殊區塊要有明確的偵測與隔離處理。
  - 每個階段可單獨測試與替換。

---

## 方法（如何達到目標）
整體方法採用「管線式（Pipeline）」設計：每一階段只做一類轉換，輸出給下一階段使用。

### 1) 前處理：把輸入切成可控單位（Lines）
- 對應函式：`preprocessCaseToLines`
- 目的：
  - 處理原始換行風格（例如 CRLF/LF）、去除不必要的尾端空白。
  - 將輸入切成「行」的陣列，讓後續演算法以 line-based 運作。
- 產出：`string[] lines`

### 2) 詞法分析：把每行變成 token（縮排／內容／符號線索）
- 對應函式：`tokenizeLine`
- 目的：
  - 把「行」拆成具有語意的 token：例如 `indent`、`marker`（項目符號/編號型態）、`text` 等。
  - 在此階段保留足夠線索，避免太早做結構決策（例如不要直接把所有縮排視為層級）。
- 產出：`Token[]`（或每行一組 tokens / lineToken）

> 設計觀點：  
> 這一層通常是「可擴充的特徵萃取」。未來若加入「特徵字偵測」或更多編號規則，多半落在 `tokenizeLine` 及其規則表，而不是散落在建樹邏輯。

### 3) 區塊偵測：先隔離表格等特殊結構
- 對應函式：`detectTableBlocks`
- 目的：
  - 從 line tokens 中找出「疑似表格」的連續區段，形成 block。
  - 對表格 block 套用不同的解析或保留策略，避免被一般清單/縮排規則誤判。
- 產出：`Block[]`（例如 `table block` + `normal text block`）

### 4) 建立初步樹狀結構：以相對縮排與符號關係建樹
- 對應函式：`buildTree`（或版本演進：`buildTree_v1`）
- 目的：
  - 將 blocks/lines 轉成階層樹（parent/child/sibling）。
  - 核心策略通常是「維護縮排歷史（stack）」：  
    - 縮排增加 → 推入堆疊，成為 child  
    - 縮排相同 → sibling  
    - 縮排減少 → pop 直到找到對應層級
  - 同時利用 `marker` 類型輔助判斷（無序/有序、同級可並列等）。

> 備註：  
> 「斷行修復（內容延續）」若採用特徵字判斷（例如：下一行開頭不是常見 marker 且縮排不小於上一行 → concat），實作上可放在：
> - `preprocessCaseToLines`（偏文字層面合併），或
> - `buildTree` 前（先以 token 決定合併），  
> 取決於團隊希望「合併」被視為文字清理還是結構推論。

### 5) 正規化：把「可解析但不一致」的樹整理成一致形狀
- 對應函式：`normalizeTree`
- 目的：
  - 修正建樹階段因資料雜訊造成的局部不一致（例如：空白行、異常跳階、混用編號層級）。
  - 合併可合併的文字節點、清理空節點、統一節點型別與欄位。
- 產出：穩定的 normalized tree，提供給呼叫端或渲染層。

### 6) 統一封裝：parseComment 作為對外 API
- 對應函式：`parseComment`
- 角色定位：
  - 作為「流程編排器（orchestrator）」：依序呼叫  
    `preprocessCaseToLines → tokenizeLine → detectTableBlocks → buildTree → normalizeTree`
  - 對外提供單一入口，使上層只需關心輸入/輸出，不需理解中間細節。

## 附註：測試與演進方式（與設計的關係）
現有測試（例如 `tests/註釋排版/parseComment_test.js`、`tokenizeLine_test.js`、`detectTableBlocks_test.js`、`buildTree_test.js`、`normalizeTree_test.js`）反映此設計的意圖：  
- 每個階段都可被獨立餵資料、獨立驗證輸出。  
- 新增規則（例如新的 marker、表格偵測例外、斷行修復策略）可先在對應階段加測，再調整實作，降低回歸風險。
