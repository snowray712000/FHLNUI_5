# 18 smart table 解耦重構教學

## 目的

這份文件用來整理 [18_smart_table_joTable_demo.js](./18_smart_table_joTable_demo.js) 的架構分析，重點不是單純把大函式切小，而是降低耦合，讓後續 mode、注腳、複製、對話框整合可以分開演進。

## 先講結論

目前版本已經值得重構。

原因不是只有函式偏長，而是以下幾種變動來源集中在同一個 script module：

1. UI DOM 綁定
2. 遠端資料查詢
3. 經文資料轉換
4. 段落與併節規則
5. table rendering
6. selection 與 copy
7. progressive footnote loading
8. window.Ijnjs 對話框整合

只要其中一塊修改，通常就要回頭碰同一支主檔，這就是高耦合的實際症狀。

## 目前主要模組與責任

| 模組 | 角色 | 觀察 |
| --- | --- | --- |
| `18_smart_table_joTable_demo.js` | 頁面主控制腳本 | 知道太多，責任過度集中 |
| `TableSelector.js` | 表格選取狀態機 | 邊界清楚，適合保留 |
| `CtxMenu.js` | 右鍵選單 UI 元件 | 邊界清楚，適合保留 |
| `cvt_others.js` | 原始經文轉 DText | 偏 domain transform |
| `dtexts_render.js` | DText 轉畫面片段 | 偏 renderer adapter |
| `grouping_by_paragraph_for_dtexts_with_addr.js` | 段落分組規則 | 偏 layout/domain rule |
| `queryFootsAsync.js` | 注腳查詢與回填 | 偏 async service |
| `loadAndDecompressJsonGzAsync.es2023.js` | 載入段落資料 | 基礎設施工具 |
| `BibleConstant.es2023.js` / `BibleConstantHelper.es2023.js` | 聖經常數與地址換算 | 穩定 utility |

## 目前依賴關係

高層依賴可以簡化成：

```text
UI DOM
  -> 18_smart_table_joTable_demo.js
  -> fetch API / paragraph json / window.Ijnjs
  -> TableSelector / CtxMenu
  -> cvt_others / dtexts_render / queryFootsAsync
  -> BibleConstant / BibleConstantHelper
```

主流程又可以拆成三條鏈：

### 1. 載入鏈

```text
初始化或按鈕事件
  -> loadTable
  -> fetchVersion
  -> renderToContainer
  -> buildColTable / buildRowTable
```

### 2. 資料轉換鏈

```text
API record
  -> BibleConstantHelper.getBookId
  -> cvt_others
  -> buildParaGroups
  -> dtexts_render
  -> DOM
```

### 3. 互動鏈

```text
TableSelector event
  -> setupSelector
  -> badge / status / ctxMenu / copyOutput
  -> buildCopyData
  -> clipboard
```

問題不是依賴數量，而是全部直接連到同一個檔案，中間沒有 controller、service、repository、adapter 這些邊界。

## 高耦合與高變動風險

### 模組級共享狀態

`paragraphData`、`currentMode`、`currentBook`、`currentChap`、`currentVersions`、`rspArrCache`、`snVisible` 都放在同一層。

風險：

1. 任一功能調整都可能影響其他流程
2. 很難做局部測試
3. 初始化順序容易變成隱性前提

### renderToContainer 知道太多

這個函式同時處理：

1. record 轉位址
2. cvt_others
3. footWork 收集
4. paraGroups 建構
5. table DOM 建立
6. selector 安裝
7. 注腳 progressive loading

風險：

只要其中一段換做法，例如 footnote 更新策略改掉，整個 rendering orchestration 就要連帶調整。

### buildParaGroups 混合兩種規則層次

這裡把「併入上節」與「段落分組」綁在一起。

風險：

1. 併節規則調整時，段落模式也要一起驗證
2. mode 1/2 與 3/4 的差異無法獨立演進
3. domain rule 與 layout rule 混在同一個函式

### UI 與外部整合直接硬接

DOM 在檔案開頭直接抓取，對話框透過 `window.Ijnjs` 直接調用。

風險：

1. 測試替身不容易塞入
2. 初始化時序脆弱
3. 這個 demo 無法乾淨重用到別的頁面

## 哪些地方違反單一職責

### `18_smart_table_joTable_demo.js`

它實際上同時扮演：

1. controller
2. view glue code
3. repository client
4. layout coordinator
5. copy service
6. footnote updater
7. dialog adapter

這已經不是單一職責，而是整個頁面所有角色的集合。

### `renderToContainer`

這是典型 god function。它知道資料格式、版面策略、DOM 結構與後續非同步更新方式。

### `loadTable`

名稱看起來像 data loader，但實際還負責：

1. 更新 state
2. 控制 loading UI
3. 觸發 render
4. 更新按鈕文案

### `buildCopyData`

它不只做 copy data，還知道：

1. DOM selection 結構
2. 表格分組規則
3. SN 顯示策略
4. HTML 與 plain text 匯出格式

## 建議拆分方式

## 第一層：先切出穩定邊界

### 1. ScriptureRepository

負責：

1. `fetchVersion`
2. 多譯本查詢協調
3. API request/response 格式封裝

切出的原因：

主控制器不應直接知道 API URL、POST body、版本欄位補值等細節。

### 2. ParagraphRepository

負責：

1. 載入 `paragraphs_ncv.json.gz`
2. 回傳 paragraph data

切出的原因：

這是資料來源問題，不是頁面控制問題。

### 3. VerseLayoutService

負責：

1. merge with previous verse 規則
2. paragraph grouping 規則
3. mode 1 到 4 所需的 layout model

切出的原因：

這是高變動的 domain/layout 規則，應能單獨測試。

## 第二層：把畫面與互動拆開

### 4. LectureTableRenderer

負責：

1. 輸入 table model
2. 輸出 table DOM
3. mode 1/3 與 2/4 的結構差異

切出的原因：

controller 不應自己操作 row、cell、rowspan、dataset。

參考：

同專案的 `16_smart_table_joTable_demo.js` 與 `TableRenderer.js` 已經示範了資料模型先行、renderer 後處理的方向。

### 5. SelectionPresenter

負責：

1. 接 `TableSelector` 事件
2. 更新 badge / status / button state
3. 決定何時顯示 `CtxMenu`

切出的原因：

`TableSelector` 已經很乾淨，不需要再把 UI 面板更新邏輯塞回主控制器。

### 6. CopyService

負責：

1. 接收 selected cell model
2. 產出 plain text
3. 產出 HTML table
4. 寫入 clipboard

切出的原因：

複製規則本身是一個完整 use case，不應與 DOM 查找綁死。

## 第三層：把外部系統包成 adapter

### 7. FootnoteService

負責：

1. 查詢注腳
2. 發出注腳更新事件或 callback

切出的原因：

service 不應直接 query 畫面 DOM。它應只回報哪個 record 更新了，由 controller 或 renderer patch UI。

### 8. DialogAdapter

負責：

1. book/chap dialog
2. version dialog
3. 將 `window.Ijnjs` 差異包起來

切出的原因：

這是外部全域依賴，最不應擴散到主流程。

## 建議依賴方向

```text
View
  -> Controller
  -> Application Services
  -> Domain Services / Repository / Adapter
  -> Infrastructure
```

重點是不要再讓 renderer、copy、footnote service 反過來知道 controller 內部狀態。

## 建議重構順序

### 第一步

先抽 `ScriptureRepository`、`ParagraphRepository`、`VerseLayoutService`。

原因：

這一步最能降低主檔知道太多的問題，而且對 UI 行為影響相對小。

### 第二步

抽 `LectureTableRenderer`，讓主控制器只負責「給 model、收 DOM」。

### 第三步

抽 `SelectionPresenter` 與 `CopyService`。

### 第四步

最後再把 `FootnoteService` 與 `DialogAdapter` 收斂進去。

原因：

它們牽涉外部非同步與初始化時序，放後面比較安全。

## 驗證清單

重構後至少要驗證：

1. mode 1 到 4 顯示一致
2. 顯示譯本切換正常
3. SN 顯示切換正常
4. 單格與矩形選取正常
5. copy plain text 正常
6. copy HTML table 正常
7. footnote progressive update 正常
8. book/chap dialog 與 version dialog 正常
